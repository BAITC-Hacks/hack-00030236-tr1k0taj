# Agent kernel v1: план и контракт реализации

- Статус: принято к реализации по запросу владельца, 2026-09-23.
- Ветка: `feat/blackboard-core`, основа: `main` после merge PR #2 (`744a7dd`).
- Этот документ публикуется отдельным коммитом **до кода**.
- Связанные решения: ADR 0009, ADR 0002–0008, `knowledge-module.md`.

## 1. Результат и границы

Рабочее backend-ядро: один главный агент, N настраиваемых фоновых агентов,
append-only blackboard в Postgres, асинхронный оркестратор, RAG-инструменты,
streaming API, прерывание и история с состоянием воспроизведения.
Главный использует новые фоновые результаты внутри текущего ответа.
Фон публикует только внутренние результаты, пользовательский текст выдаёт главный.

Существующие FastAPI, SQLAlchemy async, Alembic, Postgres и Next proxy сохраняются.
Один backend worker; активные задачи живут в `asyncio`, Redis/Celery не нужны.
После рестарта незавершённые сессии закрываются с явным событием, история сохраняется.
Аудиозапись, STT/TTS и UI реализуются соседними компонентами; ядро принимает текст
и отдаёт поток текстовых сегментов с контрактом обратной связи о воспроизведении.
Это ядро, а не заявление о готовности всех страховых действий/роутера хакатона.

## 3. Сегменты главного ответа

Один `response_id` содержит упорядоченные `segment_id`. Каждый сегмент — короткая
часть ответа (обычно предложение), текст внутри него отдаётся по мере генерации.
Перед следующим сегментом модель получает актуальный ContextPackage, включая
новые принятые результаты фона. Уже опубликованный префикс неизменяем.
Управляющие поля завершения и вызовы инструментов не попадают в пользовательский текст.
Начатый вызов модели не меняет свой prompt магически: новые данные влияют на следующую
генерацию **в том же ответе**. После завершения ответа фон остаётся для следующего хода.
Не продлеваем законченный ответ бессмысленными фразами ради ожидания фона.

Дефолт: не более 4 сегментов на ответ, 3 циклов инструментов на сегмент,
60 секунд на ответ; лимиты задаются серверной конфигурацией.
Ошибка после частичного текста сохраняет выданный текст и завершает ответ как failed;
не повторяем опубликованный префикс автоматическим retry.
Обязательные факты получаем до утверждения факта; фон не оправдывает выдуманные ответы.

## 4. Контракты состояния

Все публичные модели — `backend/app/schemas/kernel.py`, extra-поля запроса запрещены.
UUID используются для session/response/segment/event request identifiers.

- Session: `session_id`, `generation`, `input_revision`, `status`, `next_turn_id`,
  `active_response_id`, `agents`, ограниченный структурированный `context`.
- BoardEvent: `session_id`, `seq`, `event_id`, `type`, `visibility` (public/internal),
  `author`, `turn_id`, `response_id`, `segment_id`, `generation`, `input_revision`,
  `caused_by`, `payload`, `created_at`.
- AgentSpec: `agent_id`, `instructions`, `on` (user.message / agent.result),
  `depends_on` (agent IDs), разрешённые tool names, timeout. Конфигурация задаётся
  при создании сессии, ограничена по числу/размеру, циклы зависимостей запрещены.
- AgentRun: `run_id`, agent_id, turn_id, generation, input_revision, dependencies,
  status queued/running/completed/failed/stale/cancelled, result/error; хранится событиями.
- ResponseSegment: ID, индекс, текст, generating/completed/interrupted/failed,
  used_source_ids, consumed_board_seq; playback timeline и подтверждение отдельными событиями.

`seq` — порядок в журнале, не версия актуальности задачи. `input_revision` растёт
при новом пользовательском вводе/изменении значимого исходного контекста. Принятие
двух независимых фоновых результатов одной ревизии не инвалидирует второй.
Результаты предыдущей ревизии сохраняются как stale и не входят в новый ответ.
Прерывание само по себе не меняет input_revision; новый ввод меняет.
Новая сессия/смена идентичности запрещает применение старого поколения.
Публикацию и отмену сериализует короткий session lock, сетевые ожидания проходят вне lock.
Перед каждой дельтой проверяется active response и отмена; идентификатор ответа не переиспользуется.

## 5. Оркестратор

Кодовый планировщик получает события `user.message` и принятые `agent.result`.
Токены, тайминги и playback не запускают агентов. Каждый агент запускается не более
одного раза на input_revision после выполнения своих зависимостей.
N конфигурируется, дефолт два фоновых читателя KB; глобальный semaphore ограничивает
одновременные вызовы, на сессию по умолчанию максимум три фоновые задачи.
Граф зависимостей ацикличен, число запусков ограничено числом агентов.
Новый ввод отменяет устаревшие задачи, stop главного сохраняет актуальный фон,
close/shutdown отменяет всё. Ошибка одного агента не останавливает остальных и main.

Результат фона — краткий вывод и факты с проверяемыми источниками, а не скрытые рассуждения.
Факты могут конфликтовать: обе записи сохраняются с происхождением, результат поиска
не является инструкцией для модели. Неподтверждённое утверждение агента не становится
автоматически фактом KB. Only-read allowlist исключает update/delete/reload/SMS/handoff.
Очередь/сигнал пробуждает обработчик; события не теряются при coalescing, они в БД.

## 6. ContextPackage и история

Пакет: текущий ввод, generation/revision, текущая тема/слоты (если переданы интеграцией),
последние ограниченные ходы, услышанные части предыдущих ответов, отдельно
partially_heard/unheard/unknown, актуальные результаты фона, источники,
уже опубликованный префикс текущего ответа, consumed event cursor.
Полная история хранится; пакет ограничен числом событий/символов и снабжён признаком
усечения. Отсечение не удаляет текущий ввод, признаки прерывания и связь фактов с источниками.
LLM-сводка старых разговоров в v1 не нужна: короткая история и структурированный контекст.

Предыдущий неуслышанный ответ нельзя считать сообщённым клиенту. Текст, для которого
нет playback подтверждения, имеет unknown, а не falsely heard. Текстовый клиент тоже
может подтвердить доставку сегмента явно через playback с соответствующим режимом.

## 7. Playback и interrupt

`played_ms` — позиция в аудиодорожке конкретного response_id, не настенные часы.
Фронт отдельно сообщает `{segment_id, start_ms, end_ms}`; интервалы не перекрываются,
порядок соответствует сегментам. Полностью пройденный интервал — heard, текущий —
partially_heard с offset, последующие — unheard. Слово по миллисекундам не угадывается.
При отсутствии интервалов сохраняем позицию и unknown; ещё не выданный/отменённый
остаток однозначно не услышан. Повторные и запоздалые acknowledgements не уменьшают
подтверждённый прогресс и не продолжают отменённый ответ.

Interrupt принимает request_id, response_id, played_ms. Атомарно помечает ответ,
записывает событие, отменяет main task/сетевой stream. Уже завершённый ответ тоже можно
пометить прерванным при проигрывании. Повторный interrupt идемпотентен; чужой response_id
не останавливает текущий ответ. Frontend сам немедленно останавливает звук и отбрасывает
поздние дельты закрытого response_id.

## 8. HTTP и события

Ниже backend-пути. В браузере к ним добавляется `/api` существующим Next proxy.

- `GET /capabilities` — режим, streaming, playback protocol, доступность модели/RAG, лимиты.
- `POST /sessions` — `{agents?: AgentSpec[], context?: object}` → session snapshot.
- `GET /sessions/{id}` — snapshot, последний seq, состояние ответа; внутреннего текста нет.
- `POST /sessions/{id}/turns` — `{request_id, text}` → 202 `{turn_id,response_id}`.
  Повтор того же request_id возвращает тот же ответ, другой payload с тем же ID — 409.
  Второй ввод при активном ответе — 409: сначала interrupt.
- `GET /sessions/{id}/events?after=N` — SSE; поддерживается `Last-Event-ID`.
  `id` — монотонный seq; replay только public событий, пробелы seq допустимы.
  heartbeat не сохраняется. Клиент дедуплицирует seq. После закрытия replay завершается.
- `POST /sessions/{id}/interrupt` — request_id, response_id, played_ms.
- `POST /sessions/{id}/playback` — request_id, response_id, played_ms,
  `segments: [{segment_id,start_ms,end_ms}]`, опционально подтверждённые текстовые сегменты.
- `GET /sessions/{id}/history` — пользовательские сообщения/ответы/сегменты и delivery status.
- `GET /sessions/{id}/trace` — проекция статусов/источников/использования фактов без сырых bg prompts/results.
- `POST /sessions/{id}/close` — идемпотентное закрытие.

События: `session.created`, `user.message`, `response.started`, `segment.started`,
`response.delta`, `segment.completed`, `response.completed`, `response.interrupted`,
`response.failed`, `session.closed`. Payload дельты содержит text и segment_id.
Служебные `agent.*`, `tool.*`, снимки контекста, ошибки с подробностями — internal.
Публичные ошибки содержат стабильный code и безопасное сообщение, без ключей/prompt.
Идентификаторы сессий — случайные; полноценная аутентификация не входит в v1.
API предназначен для доверенного хакатонного окружения, как текущий /kit CRUD.

## 9. RAG / Knowledge

Ядро импортирует `open_knowledge`/Knowledge из публичного фасада, не Store/KitRecord.
`rag_search(query, kinds, limit)` → hits с kind/key/content/source_id/score/search_mode.
`rag_read(kind,key)` → точный документ или not_found, без неявной подмены похожим.
Разрешённые kinds: kb, office, clinic, inspection_point. Клиенты/платежи и мутации
не доступны через общий документный RAG. Каждому tool call — отдельная AsyncSession.
LLM выбирает tool и аргументы; код валидирует allowlist, размеры, лимиты и таймаут.

Embeddings: конфигурируемая модель OpenAI, pgvector в той же БД, отдельная миграция.
Индекс только разрешённых документных kinds. Хеш текста и имя модели защищают от
использования устаревшего вектора после редактирования. Batch индексирование при запуске
в фоне/явной командой и после изменений; вызов модели не держит DB transaction/lock.
Объединение лексической и векторной выдачи по рангу. При недоступности/неполном индексе
явный lexical fallback; точное чтение работает без embedding API.
Каталог сценариев остаётся полным 40+3, retrieval его не фильтрует.
Dev-разметка и sample dialogs в индекс не попадают.

## 10. Проверки и критерии завершения

- [ ] Отдельный docs-коммит уже находится в удалённой feature-ветке до реализации.
- [ ] Запуск/миграции/конфигурация работают, ключ не попал в файлы Git и логи.
- [ ] SSE отдаёт несколько дельт до завершения ответа, replay без повторной генерации.
- [ ] Два фоновых результата одной ревизии принимаются; используются последующим
      сегментом того же response_id, с проверяемыми consumed event IDs.
- [ ] Tool calls выполняются реально, источники читаются через Knowledge; hybrid
      поиск проверен с OpenAI, lexical fallback обозначен явно.
- [ ] Interrupt гоняется с генерацией: после фиксации stop новых публичных дельт нет.
- [ ] played_ms и timeline дают heard/partial/unheard; без ACK остаётся unknown.
- [ ] Новый ввод/close/restart не допускают старые результаты; сессии изолированы.
- [ ] Ошибка одного агента/провайдера не теряет историю и не раскрывает внутренние сообщения.
- [ ] Повтор запросов не создаёт второй ответ; тот же ID с другим payload отклоняется.
- [ ] Проверены реальные API и Postgres, ключевые тесты и линтер; limitations записаны честно.

Тесты не используют платные API по умолчанию. Live smoke — отдельный явный рецепт.
При отсутствии Docker локально допускается описанный в justfile тестовый путь с
изолированным Postgres; это не заменяет проверку Compose, её статус указывается отдельно.

## 11. Согласование с существующими документами

ADR 0009 заменяет ограничения «один фон», «ровно два LLM-вызова», «без streaming»,
«фон влияет только на следующий ответ» и «вся доска напрямую наружу» для этого ядра.
Предметные правила кита, подтверждения действий и DATASET_TODAY сохраняются.

`scenarios: [{scenario_id, confidence, reason}]`, alternatives с scenario_id.
