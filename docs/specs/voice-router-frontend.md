# Saqta Voice — подробный промпт-ТЗ для дизайна и реализации фронтенда

Версия 1.2 · 23 сентября 2026 года · основание: репозиторий `BAITC-Hacks/hack-00030236-tr1k0taj`, коммит `2a137a4`.

Статус: подробное дизайн-дополнение и промпт для последующей реализации. Подготовка этого документа не означает, что описанные экраны или API уже реализованы. Сначала выполняется P0; расширения P1/P2 не являются условием сдачи базового Voice Router.

Этот документ можно целиком передать AI-дизайнеру или агенту, реализующему интерфейс. Он описывает пользовательский интерфейс, дизайн-систему, интерактивное поведение, демонстрационные данные и критерии проверки фронтенда. Технические решения по бэкенду в документ не входят.

## 1. Задача для исполнителя

Спроектируй и реализуй законченный, визуально последовательный фронтенд **Saqta Voice** — голосового AI-помощника страховой компании с инструментами наблюдения для супервизора. Интерфейс должен выглядеть как рабочий продукт зрелой финансовой технологической компании: спокойный, точный, современный, с хорошо организованной информацией и понятным управлением.

Главный пользовательский сценарий: человек начинает звонок, говорит в микрофон, видит свой текст и ответ помощника; супервизор наблюдает выбранные сценарии и объяснения. Параллельно один фоновый помощник собирает проверенные сведения по страховому обращению. Можно увидеть источник каждого факта и реплику, в которой факт был использован.

Работай внутри существующего `frontend/`: **Next.js 16.3.6, App Router, React 19.2.8, TypeScript**, согласно ADR 0001 и текущему `package.json`. Сохрани существующий прокси `/api/*` из `frontend/next.config.ts`. Не заменяй приложение новым проектом. Дизайн-токены, компоненты и поведение должны позволять сначала проверить интерфейс на явно обозначенных локальных данных, затем подключить согласованные события без переписывания экранов. Не создавай собственный сервер или альтернативную бизнес-логику в Next Route Handlers.

Сейчас задача заказчика — подготовить этот промпт-ТЗ, а не начать реализацию. Следующие императивы адресованы будущему исполнителю фронтенда.

Результат должен включать реализованные экраны и состояния, а не только статичную картинку. Каждый видимый элемент управления выполняет описанное действие. В демонстрационном режиме действие может работать с локальными данными, но его результат должен быть правдивым и явно обозначенным.

### 1.1. Принятые решения

- Основной формат: **единое пространство звонка с раскрываемой панелью супервизора**.
- Дополнительная возможность: **фоновый помощник по страховому обращению**, вариант 1 из плана коллеги.
- Основная навигация: **«Звонок», «История», «Сценарии»**.
- Визуальное направление: светлый интерфейс финансового продукта, графитовый текст и зелёный акцент по предоставленному референсу Halyk.
- Анимации: сдержанные, привязанные к реальным изменениям состояния.
- Страницы входа, регистрации, восстановления пароля, профиля пользователя и управления доступами отсутствуют.
- В интерфейсе используется собственное название Saqta Voice. Halyk служит цветовым референсом; логотип и название Halyk не подставляются вместо названия вымышленной страховой компании.

### 1.5. Расхождения, которые нужно учесть при подключении

В разделе 4.1 главной спеки `scenarios` — массив строк, `confidence` и `reason` находятся сверху, у альтернатив поле `id`. В `README.ru.md` исходного кита это массив объектов с `scenario_id`, `confidence`, `reason`, и у альтернатив тоже `scenario_id`. Это **реальное расхождение исходников**, а не два подтверждённых рабочих API. По правилам репозитория кит главнее. До согласования схемы фронтенд показывает интерфейс через собственную модель представления; сырой результат в диагностике сохраняет фактический формат. Нельзя молча переписывать backend-контракт или объявлять одну схему уже реализованной.

В разделе 7.1 спеки встречается `base_version`, а в 4.5 и ADR 0006 — `base_context_version`. Для будущего подключения нужен единый подтверждённый контракт. Визуально это одна версия контекста, на основе которой получен результат.

Пункт спеки о демонстрационном ключе не означает размещение ключей в браузере или исходниках. Для этой фронтенд-задачи ключи провайдеров не нужны; ошибки отсутствия конфигурации отображаются как состояние интеграции.

По исходным материалам необходимо сохранить:

- Реальный голосовой ввод и голосовой ответ в конечном продукте; текстовый ввод — резервный канал.
- Отображение маршрутизации по 40 бизнес-сценариям и трём системным исходам.
- Русский, казахский и смешанную речь.
- Транскрипт, сценарий, обоснование, альтернативы и замеры после каждой реплики.
- Ответы на основании данных; подтверждение клиентом действий, которые его требуют; уточнение и передачу оператору.
- Возможность увидеть смену темы и использование ранее найденного контекста.

Реализация LLM, STT, TTS, инструментов, API, схем хранения, очередей и бизнес-операций выполняется за пределами этого задания. Здесь задаются их видимые состояния и точки подключения к интерфейсу. Фронтенд не вычисляет решение LLM из текста и не подменяет маршрутизацию выбором пользователя в каталоге.

## 2. Приоритеты и пользовательские роли

### 2.1. Приоритеты

**P0 — обязательный законченный путь:** пространство звонка; голосовое управление; текстовый резерв; транскрипт; выбранная реплика; трассировка и «Устройство слоя»; карточка контекста; просмотр источника; состояния ожидания, ошибки, отмены и подтверждения; завершение звонка; ru/kk/mixed в разговоре; базовая адаптивность и доступность. Для UI предусматривается RU/KK. Фоновый помощник — выбранное развитие, но его подключение условно: ADR 0006 разрешает его только после гейта качества. В P0 обязательна корректная карточка и честное состояние «Помощник отключён», если функция недоступна.

**P1 — продуктовая оболочка:** история с поиском, фильтрами, пагинацией и просмотром разговора; каталог 40 сценариев и трёх системных исходов; настройки интерфейса и звука; экспорт доступных данных текущего разговора.

**P2 — дополнительное удобство:** изменение ширины правой панели; компактная плотность таблиц. Эти возможности добавляются после целостности P0 и P1. Подробная трассировка и просмотр реального промпта обязательны уже в P0.

Никакой декоративный экран не должен быть необходим для начала звонка. Первое открытие приложения приводит прямо в раздел «Звонок».

### 2.2. Пользователи

- **Участник разговора:** начинает и завершает звонок, записывает реплику, слышит ответ, при необходимости использует текст.
- **Супервизор:** наблюдает тот же разговор, выбирает реплики, смотрит сценарии, объяснения, источники и тайминги.

Это представления одного интерфейса. Для них не требуется экран входа или искусственный выбор роли перед работой.

## 3. Информационная структура

### 3.1. Оболочка приложения

- Левая навигация с логотипом Saqta Voice, тремя разделами и нижней кнопкой настроек.
- Заголовок текущего раздела, краткая поясняющая строка при необходимости и одно главное действие страницы.
- Переключатель языка интерфейса в верхней части оболочки.
- Компактный индикатор режима «Демо-данные» при работе на локальных fixtures.
- Доступность голосового соединения отображается на экране звонка; её нельзя выводить из факта, что HTML-страница загрузилась.
- Не добавлять статистические карточки, графики, меню аккаунта или колокольчик уведомлений без определённого пользовательского действия и реальных данных для них.

### 3.2. Разделы

**Звонок:** управление разговором, транскрипт, контекст обращения, помощник, просмотр маршрута конкретной реплики.

**История:** список завершённых разговоров и их результатов; переход к просмотру конкретного разговора. Просмотр истории не запускает микрофон.

**Сценарии:** справочник возможностей, условий и границ маршрутизации. Каталог имеет режим просмотра; ручное назначение маршрута активному звонку отсутствует.

**Настройки:** компактная панель, открываемая поверх текущего раздела. Это не четвёртая полноценная страница.

### 3.3. Навигационные правила

- Текущий раздел выделен цветом, текстом и состоянием выбранного пункта.
- Переход в «Историю» или «Сценарии» не создаёт новый звонок и не очищает текущий разговор.
- Во время активного разговора в этих разделах появляется компактная полоса: «Звонок продолжается · 02:14 · Вернуться». Приостановка записи из-за навигации не происходит молча.
- Запуск нового звонка при существующем незавершённом требует явного подтверждения завершения текущего.
- Действие «Назад» из просмотра истории возвращает к прежним поиску, фильтрам, странице и позиции списка.
- Прямое открытие недоступного разговора показывает конкретное состояние «Разговор не найден» с кнопкой «К истории».

- Поверхности отделять отступами, границами и фоном. Тень — только у всплывающих меню, диалогов и плавающих элементов; не под каждой карточкой.
- Иконки: единое контурное семейство, преимущественно 18–20 px. Не смешивать emoji, фотографии и разные стили иконок как обозначения действий.

### 4.4. Базовые компоненты

Предусмотреть семейства: Button, IconButton, TextField, TextArea, SearchField, Select, SearchableSelect, MultiSelect, Checkbox, Switch, SegmentedControl, Tabs, Badge, Tooltip, Popover, DropdownMenu, Dialog, Drawer, Toast, InlineNotice, EmptyState, Skeleton, DataTable, Pagination, TranscriptItem, VoiceControls, StatusIndicator, FactCard, SourceViewer, ScenarioBadge, LatencyBreakdown.

Это перечень UI-компонентов, а не требование конкретной структуры каталогов. Существующие компоненты проекта следует переиспользовать.

Для каждого интерактивного компонента определить: default, hover, focus-visible, pressed, selected при применимости, disabled, loading и error. Состояние disabled сопровождается доступным объяснением, если причина не очевидна из соседнего текста.

## 5. Компоновка и адаптивность

### 5.1. Десктоп, от 1280 px

- Sidebar: 216 px; свёрнутый вариант 72 px с подписями во всплывающих подсказках.
- Верхняя полоса: 64 px; общая навигация не занимает две строки.
- Основная область звонка: гибкая колонка разговора и контекстная панель шириной около 360–400 px.
- Ширина разговора не должна становиться меньше 520 px из-за правой панели.
- На ширине 1600 px и выше можно показать больше контекста, но ограничить длину строк транскрипта примерно 75–90 символами.
- Трассировка по умолчанию открывается как вкладка правой панели, заменяя её содержимое; опция «Развернуть» открывает широкий drawer для детального чтения.
- Поддерживать предсказуемую прокрутку каждой рабочей области. Не допускать трёх вложенных вертикальных скроллов в одной колонке.

### 5.2. Компактный ноутбук, 1024–1279 px

- Sidebar по умолчанию свёрнут.
- Правая панель может быть 320 px, если основная колонка остаётся читаемой.
- При недостатке места панель открывается поверх справа; она не уменьшает разговор до узкой полосы.
- Действия заголовка объединяются в меню «Ещё», сохраняя доступность главного действия.

### 5.3. Планшет, 768–1023 px

- Навигация открывается drawer по кнопке меню.
- Рабочая область имеет вкладки «Разговор», «Контекст», «Разбор».
- Голосовое управление закреплено внизу; переключение вкладок не сбрасывает разговор.
- У новых фактов на неактивной вкладке появляется счётчик, который снимается после просмотра.
- Таблицы переходят в компактный вид с приоритетными колонками и раскрытием строки.

### 5.4. Телефон, 360–767 px

- Одноколоночная структура, компактный header, меню навигации.
- Сохраняются вкладки рабочего пространства; нижняя панель управления учитывает safe-area и экранную клавиатуру.
- Длинные транскрипты, ID, названия сценариев и казахский текст не создают горизонтальный скролл всей страницы.
- История отображается карточками записей, а не уменьшенной таблицей на десять колонок.
- Каталог сценариев отображается карточками с ID, названием, категорией и приоритетом.
- Drawer источника и детального разбора занимает почти весь экран и имеет явную кнопку закрытия.
- Фильтры открываются в панели с кнопками «Показать результаты» и «Сбросить»; число активных фильтров видно до открытия.
- При увеличении масштаба интерфейс сохраняет доступ к контенту и действиям; фиксированные высоты не обрезают текст.

## 6. Общие правила интерактивности

- Действие даёт видимую обратную связь сразу: состояние кнопки, spinner, сообщение или изменение содержимого.
- Не показывать успех до получения успешного результата соответствующего обработчика или явно локальной операции демо.
- Исключить повторную отправку действия двойным кликом; во время обработки сохранять понятное состояние.
- Нельзя рисовать завершённый процент выполнения для операции, у которой нет измеримого прогресса.
- Ошибка одного блока не скрывает остальные рабочие части страницы.
- Данные другого звонка не должны кратко появляться при переключении записей; при загрузке показывается skeleton правильного блока.
- Для пустого исходного списка, отсутствия результатов фильтра и ошибки загрузки использовать разные сообщения и действия.
- Формы сохраняют введённый текст после ошибки; сброс ввода происходит только по ясному действию пользователя или подтверждённому успеху.
- Закрытие popover не должно завершать звонок, останавливать запись или менять фильтры, которые требуют отдельного применения.
- Отмена модального диалога возвращает прежнее состояние и фокус на открывший его элемент.

## 7. Экран «Звонок»: состав и иерархия

### 7.1. Верхняя часть

Заголовок «Звонок», краткое назначение «Голосовой помощник Saqta Insurance». Под ним компактная строка: состояние разговора, продолжительность, язык последнего распознанного сообщения. Справа — «Новый звонок» и меню «Ещё». Продолжительность появляется после фактического старта сессии и останавливается при завершении; это не время работы приложения и не задержка ответа.

Первый экран не должен выглядеть пустой админкой. В центральной области — заголовок «Расскажите, чем помочь», подпись «Задайте вопрос о полисе, страховом случае или документах. Можно говорить на русском и казахском», основная кнопка «Начать разговор», вторичная ссылка «Написать текстом». Ниже — 2–3 коротких примера из `scenarios.json`. Пример заполняет текстовый черновик и никогда не отправляется автоматически. Никакой автоматической предзагрузки личности C004 до её идентификации.

В правой области до появления данных — спокойное пояснение «Здесь появятся сведения по вашему вопросу». Если открыт «Разбор», вместо фиктивных цифр показать «Выберите реплику после начала разговора».

### 7.2. Основная композиция

1. Слева — текущая тема, хронологический транскрипт и постоянно доступное управление вводом.
2. Справа — две вкладки «Контекст» и «Разбор». В «Разборе» есть доступ к «Устройству слоя».
3. В контексте — идентификация, обращение/полис/платёж по текущему вопросу, следующий шаг, подтверждённые факты, карточка фонового помощника.
4. Выбор старой реплики меняет «Разбор», но не превращает текущий контекст в прошлое состояние без подписи. Для исторического снимка нужен явный заголовок «Контекст на реплике 3».
5. Сведения об офисе или вопросе по оплате не надо втискивать в карточку обращения: показывай секции, для которых действительно есть данные. Секция с неизвестным значением не заполняется придуманным примером.

У центральной колонки должен быть больший визуальный вес. В обычном состоянии достаточно одного зелёного основного действия, а диагностические данные раскрываются по запросу. Не открывать JSON поверх разговора автоматически.

### 7.3. Состояния разговора и доступные действия

- **До начала:** «Начать разговор», «Написать текстом». Устройство запрашивается только по действию пользователя.
- **Создаём сессию:** кнопка показывает ожидание; повторный старт исключён. Ошибка возвращает возможность повторить.
- **Готов к реплике:** «Записать реплику», резервный текст и «Завершить звонок» доступны.
- **Записываем:** таймер записи и индикатор уровня звука; «Отправить запись», «Отменить запись». «Новый звонок» требует подтверждения с предупреждением о потере неотправленной записи.
- **Отправляем/распознаём:** видимый статус, отмена текущего хода. Никакого выдуманного транскрипта до результата STT.
- **Обрабатываем вопрос:** показать реальный полученный этап: «Выбираем сценарий», «Проверяем данные», «Готовим ответ». Если отдельных событий нет, использовать единое «Обрабатываем вопрос», а не таймерное переключение этапов.
- **Готовим звук:** текст ответа может быть уже виден. Ожидание звука не выдаётся за его воспроизведение.
- **Ответ звучит:** видимое «Отвечаем» и «Остановить ответ». Новый голосовой и текстовый ввод заблокирован до окончания либо остановки, как требует раздел 7.5 главной спеки.
- **Ждём уточнения:** вопрос бота остаётся в транскрипте; стандартный ввод вновь доступен. При двух предложенных вариантах их кнопки доступны только как реплика клиента.
- **Ждём подтверждения:** карточка preview, точные параметры и действия из раздела 10. Новый ввод разрешён для согласия, отказа или исправления.
- **Передача оператору:** отображается её реальное состояние; «оператор подключился» без подтверждённого события не показывается. Мок явно подписан.
- **Восстанавливаем соединение:** последнее содержимое сохранено, повторные отправки отключены, есть понятное объяснение. Автоматический повтор допустим только для чтений, не для необратимых действий.
- **Завершён:** неизменяемый транскрипт, результат разговора и «Новый звонок». Микрофон выключен, фон остановлен; окончание звонка не означает урегулирование страхового случая.

Состояния подключения, текущего хода, записи, звука и помощника независимы. Не делай один флаг `isLoading`, который блокирует всё приложение из-за фонового поиска.

### 7.4. Завершение, остановка и новая сессия

«Остановить ответ» прекращает воспроизведение и отменяет текущий foreground-ход, сохраняя сам разговор. Уже видимый текст остаётся с пометкой «Ответ остановлен», запоздалые продолжения игнорируются. После локальной остановки звука нельзя объявлять серверную отмену успешной без поддержки контракта. Неопределённый исход действий показывается отдельно и не повторяется автоматически.

«Отменить запись» удаляет только ещё не отправленную запись. «Завершить звонок» закрывает текущую сессию. «Новый звонок» создаёт чистую сессию с новым идентификатором; никакие клиент, слоты, согласия и факты не переносятся. Локальная защита от старых ответов срабатывает сразу, серверная отмена привязывается к согласованному обработчику.

Для активного звонка «Новый звонок» открывает диалог: «Завершить текущий разговор и начать новый?»; подпись «Новая сессия начнётся без данных этого клиента». Действия: «Продолжить разговор» и «Завершить и начать новый». Если готового API нет, в UI-прототипе очищается только локальная демонстрационная сессия и это не объявляется серверным действием.

После завершения не открывать рейтинг, NPS, оценку сотрудника или рекламное предложение — таких требований нет. При `SYS_GOODBYE` отображать прощание; финальное закрытие следовать событию исполнителя, учитывая проигрывание последнего аудио.

## 8. Голос, текст и транскрипт

### 8.1. Управление записью

Для первой версии используй запись одной реплики: нажатие «Записать реплику» начинает запись, «Отправить запись» завершает и отправляет. Это управляемый вариант push-to-talk без удержания мыши, подходящий также клавиатуре и touch. Переключение в удержание — дополнительная настройка будущего, сейчас не нужна. Пассивного прослушивания и barge-in нет.

- При первом нажатии запускается браузерный запрос разрешения. Рядом показать «Разрешите доступ к микрофону в браузере»; собственный диалог не имитирует системное разрешение.
- Во время записи видны красный значок, текст «Идёт запись» и отдельный таймер. Красный здесь означает активный захват, а не ошибку.
- Волна реагирует на фактическую амплитуду. При отсутствии доступа или сигнала полосы не танцуют. При reduced motion достаточно шкалы уровня и текста.
- Ограничение длительности берётся из согласованной возможности речевого тракта. До этого в прототипе можно задать локальный предел 60 секунд с подписью о лимите записи; это UX-допущение, не требование к backend. При достижении предела запись останавливается и предлагает отправить/перезаписать, не отправляется без ясного действия.
- Проверять поддержку формата записи; не объявлять любой blob WAV. MIME и максимальный размер согласовываются с речевым адаптером, а не придумываются компонентом.
- При закрытии сессии останавливаются все дорожки MediaStream. При обычном переходе в историю текущая запись остаётся под управлением общей полосы звонка.
- «Стоп» должен быть доступен и вне вкладки звонка. Если мини-полоса не умеет завершать запись, переход при записи должен сначала явно предложить отправить или отменить её.

### 8.2. Ошибки голоса

- **Нет разрешения:** «Доступ к микрофону запрещён. Разрешите его в настройках сайта или напишите сообщение». Действия «Проверить снова» и «Написать текстом».
- **Нет устройства:** «Микрофон не найден. Подключите устройство и повторите проверку». Не запускать бесконечные запросы разрешения.
- **Устройство занято/отключено:** остановить индикатор записи, сохранить уже записанный фрагмент только если он пригоден; предложить повторную запись. Не утверждать, что реплика отправлена.
- **Неподходящий контекст страницы:** понятное сообщение о доступе через localhost/HTTPS. Текстовый канал остаётся доступным, если соединение с backend работает.
- **Речь не распознана:** «Не удалось разобрать запись. Повторите или введите текст». Исходный failed-элемент сохраняет статус; повтор не создаёт два одинаковых успешных хода.
- **Ошибка TTS:** текст ответа сохраняется, «Не удалось озвучить ответ», доступно «Повторить озвучивание», если это поддержано. Повтор звука не запускает бизнес-действие снова.
- **Браузер заблокировал воспроизведение:** «Нажмите, чтобы прослушать ответ»; явная кнопка воспроизведения. До её фактического старта не фиксировать начало звука.
- **Нет ключей или провайдер недоступен:** короткое объяснение, резервный канал в пределах его доступности, диагностический код по раскрытию. Фронтенд не предлагает ввести API-ключ на странице.

### 8.3. Текстовый резерв

Ссылка «Написать текстом» раскрывает компактную textarea под транскриптом. Placeholder: «Напишите вопрос о страховке…». Кнопка «Отправить», подсказка «Enter — отправить, Shift+Enter — новая строка»; при вводе через IME Enter не отправляет незавершённую композицию.

Пустое или состоящее из пробелов сообщение не отправляется. Лимит текста — согласованная capability; для локального прототипа 2000 символов. Счётчик появляется после 80% лимита; превышение объясняется рядом с полем. Черновик сохраняется при переключении вкладок, изменении языка UI и ошибке запроса. Во время foreground-обработки запрещена повторная отправка и новый ввод согласно основной спеке; текст уже набранного черновика сохраняется.

После успеха поле очищается, фокус остаётся в логичной точке. После ошибки сохранённое сообщение допускает исправление и повтор. Использованный канал отмечается у реплики «Текст» или «Голос». Текстовый режим не получает фиктивный STT-тайминг.

### 8.4. Структура элемента транскрипта

Для каждой реплики: автор «Клиент»/«Saqta Voice», время, текст, языковая метка при наличии результата, статус отправки/обработки и кнопка «Разобрать» для клиентского хода. Сервисные события вроде передачи оператору — отдельная тонкая строка с текстом, а не сообщение от клиента.

Не использовать аватары с фотографиями. Различие участников — выравнивание, подпись и мягкий фон; большие ярко-зелёные пузыри не нужны. Текст можно выделить и скопировать без открытия разбора. Для копирования отдельная кнопка в меню элемента; успех — только после успешного Clipboard API, иначе предложить выделить текст.

Ответ бота отображается целиком при получении готового текста. Искусственная печать по буквам не нужна. Партиалы допускаются только при фактическом streaming; они имеют пометку «Распознаём» и заменяются итоговой репликой без дублирования. В текущем режиме ожидается только финальный STT.

Язык `mixed` показывается как «Смешанная речь». Если backend предоставил сегменты, на раскрытии показать принадлежность сегментов языкам; фронтенд не определяет её по символам. Нет сегментов — «Разметка по сегментам недоступна».

### 8.5. Автопрокрутка и выбор хода

Автопрокрутка работает, пока пользователь находится у конца списка (порог 80 px). Если он ушёл выше, новые сообщения не сдвигают чтение; появляется кнопка «Новые сообщения · N». Нажатие прокручивает вниз и сбрасывает счётчик. В reduced motion перемещение мгновенное.

Выбранная реплика получает спокойную зелёную рамку и доступное selected-состояние. В разборе всегда видны номер хода и короткий фрагмент выбранной реплики. Автоматический просмотр последней реплики прекращается, если пользователь вручную выбрал старую; есть «К последней реплике». Новое событие не перехватывает фокус.

Для демонстрационных диалогов до 10 реплик **пагинация транскрипта не нужна**. Не обрезать разговор и не завершать его автоматически после десятой клиентской фразы: лимит — объём демо, а принудительное закрытие требует отдельного контрактного правила. Пагинация применяется к истории и каталогу.

## 9. Контекст, факты и фоновый помощник

### 9.1. Идентификация и данные

До идентификации: «Клиент пока не определён» и описание, что бот уточнит необходимые сведения. Не делать отдельную страницу авторизации: идентификация внутри страхового сценария сохраняется как часть разговора.

После подтверждённого результата: имя, маскированный телефон, город при наличии. Ниже — номер и тип обращения, статус на русском/казахском, недостающие документы и следующий шаг. Для `documents_requested` показывать «Ожидаются документы», а исходный код — только в деталях. Не путать статус обращения со статусом звонка.

Номер обращения доступен для копирования. ИИН и контактные значения маскируются по умолчанию; полного профиля клиента, редактируемой CRM-карточки и случайных финансовых показателей нет. Любое раскрытие сведений — только из уже разрешённого текущему представлению набора.

Если найдено несколько обращений, клиент уточняет выбор голосом/текстом либо специальной клиентской кнопкой, которая отправляет явный выбор как реплику. Наблюдатель не меняет привязку скрытым кликом в карточке. При неизвестном ID показать отсутствие совпадения, а не ближайшего клиента.

### 9.2. Карточка факта

Каждый факт содержит: короткую понятную формулировку, источник, ID источника по раскрытию, происхождение («Данные обращения»/«Найдено помощником»), состояние актуальности. Если контракт сообщает использование — «Использовано в ответе на реплику 5», ссылка ведёт к соответствующей реплике.

Метка «Проверено» допустима только для данных из разрешённого источника, не для произвольного текста модели. Факт, применённый к контексту, ещё не обязательно использован в ответе: это два различных состояния. При отсутствии события использования не выводить такую метку по совпадению слов.

Повторное получение идентичного факта не создаёт дубль. Если значение изменилось, карточка явно показывает актуальное значение и позволяет увидеть предыдущее в разборе; конфликт разрешается исполнителем, не фронтендом. Устаревшие результаты не смешиваются с актуальными фактами.

### 9.3. Просмотр источника

Кнопка с названием источника открывает drawer: заголовок «Источник факта», краткий факт, имя операции (`get_claim`, `kb_lookup` и др.), `source_id`, время получения, связанный ход, релевантный фрагмент данных. Если исходный фрагмент не получен, написать «Доступна только ссылка на запись источника». Не генерировать цитату из ответа бота.

Ссылка `source_id` сама по себе не URL. Она открывает внутреннее представление; внешний переход доступен только при наличии разрешённого URL в данных. Содержимое источника выводится как текст/безопасная разметка, HTML и скрипты из него не выполняются. Меню копирования предлагает факт и ссылку на источник отдельно.

Закрытие возвращает в прежнее место правой панели с прежним фокусом. Открытие источника не очищает выбранную реплику и не останавливает разговор. На телефоне используется один полноэкранный drawer с внутренней кнопкой «Назад», а не стопка модальных окон.

### 9.4. Помощник: независимые состояния

- **Отключён:** «Фоновый помощник отключён в этой сборке». Основные факты и разговор работают. Не отображать имитацию поиска.
- **Ожидает контекст:** «Помощник начнёт поиск, когда появятся данные по вопросу».
- **Ищет:** название реального чтения, если известно, и неопределённый индикатор; «Разговор можно продолжать». Поиск не блокирует микрофон, если foreground свободен.
- **Есть ожидающее обновление:** небольшая подпись «После текущего поиска проверим новый вопрос» только при наличии такого состояния; не очередь из десятков задач.
- **Результат получен:** найденные сведения и источники; применение к контексту показывается отдельно от получения.
- **Применён:** «Контекст дополнен», привязка к версии в деталях. Уже звучащий ответ не заменяется.
- **Дополнительных сведений нет:** честное завершённое пустое состояние без ошибки.
- **Ошибка:** «Не удалось получить дополнительные сведения. Разговор продолжается». Повтор возможен только через поддержанный обработчик со свежим контекстом.
- **Устарел:** «Контекст изменился — этот результат не использован». Нейтральный статус, не красный сбой. Причина/версия доступны в разборе.
- **Отменён:** «Поиск остановлен после завершения звонка» либо соответствующая причина. Действий повтора для закрытой сессии нет.

При новом клиенте, `generation` или сессии все результаты старого контекста исчезают из текущей карточки; позднее событие может остаться в журнале своей сессии, но не обновляет новую. UI не присваивает себе право принимать или отклонять серверный патч: оно показывает авторитетный исход и дополнительно защищается от чужих событий.

### 9.5. Активная и отложенные темы

Над транскриптом показывается компактная метка текущей темы: `SC17 · Статус обращения`. Если тема неизвестна, «Уточняем вопрос». Для нескольких намерений — упорядоченные метки, срочное первым согласно результату исполнителя.

Отложенные темы раскрываются через «Ещё вопросы · N». Содержимое: название, состояние «Ожидает возвращения», известные параметры в маскированном виде. Это отражение `pending_topics`, а не редактор очереди. Просмотр не вызывает бизнес-переход. Возвращение к теме происходит через реплику клиента либо подтверждённый контрактом пользовательский выбор.

При уходе к вопросу об офисе сведения об обращении сохраняются с подписью, что это контекст предыдущей темы. При возвращении объяснимо видно, что известный номер обращения не запрошен повторно. Не добавлять полноценный секретарь нескольких задач сверх этого поведения.

## 10. Уточнения, подтверждения и оператор

### 10.1. Уточнение маршрута

При `SYS_UNCLEAR` бот задаёт короткий вопрос, если получены варианты — до двух кнопок с понятными названиями. Кнопка отправляет ответ клиента через тот же путь, что текст, и не назначает `scenario_id` напрямую. После выбора кнопки блокируются для этой реплики и остаются видны как контекст. Если отправка не удалась, выбор можно повторить без дубликата успешного хода.

Не показывать пользователю требование «выбрать confidence». Пороговую политику исполняет backend; frontend отображает её результат.

### 10.2. Карточка подтверждения

Preview располагается в транскрипте рядом с ответом бота и повторяется компактно в контексте. Состав: «Подтвердите изменение», описание действия, текущие и новые значения, ссылка на исходную реплику, состояние согласия.

В клиентской области доступны «Подтверждаю» и «Не менять»; при необходимости «Исправить» фокусирует текстовый ввод с пояснением, какие сведения уточнить. В панели супервизора — только наблюдение. Клиентские кнопки должны быть явно подписаны как ответы участника разговора, чтобы наблюдатель не выглядел обладателем права согласия за клиента.

До появления согласованного API безопасный вариант — отправить явную реплику клиента по существующему каналу. Фронтенд не вызывает отдельный придуманный endpoint подтверждения. При подключении специального обработчика он должен ссылаться на актуальные action/params/turn, определённые backend.

После нажатия: «Подтверждение отправляется» → реальный исход. Двойной клик не повторяет действие. После исправления параметров старые кнопки сразу становятся неактуальными; требуется новый preview. Отказ не должен оставлять зелёную карточку успеха.

Варианты исхода: «Изменение выполнено», «Изменение отменено», «Подтверждение устарело — проверьте новые данные», «Не удалось выполнить изменение», «Результат выполнения пока неизвестен». Последний вариант важен при потере связи после отправки; предлагать проверить состояние, а не слепо повторить операцию.

### 10.3. Передача оператору

Карточка содержит причину передачи, очередь при наличии, краткое резюме текущей темы, идентификацию в маскированном виде, существенные факты и следующий шаг. Показывать «Передача оператору · демонстрация» для мок-результата. Текст после успешного мока: «Контекст подготовлен для оператора. В этой версии передача демонстрационная».

Не рисовать счётчик очереди, ожидаемое время ожидания, имя оператора и фотографию без источника. Статусы: готовится / передано в мок / ошибка / недоступно. Реальная передача и мок — разные подписи. Нельзя обещать выплату, автоматический выпуск полиса или возврат денег.

Для SC30: показать платёж и отсутствие выпущенного полиса по источнику, затем `operator_general`. Завершение такой сессии — «Передано оператору», а не «Проблема решена». Для неподдержанного действия карточка объясняет передачу, сохраняя выбранный сценарий в разборе.

## 11. Панель супервизора: «Разбор» и «Устройство слоя»

### 11.1. Разбор конкретной реплики

Верхняя строка: «Реплика 3 из 6», предыдущая/следующая, выпадающий выбор хода с короткими фрагментами текста, «К последней», «Развернуть». Номер — порядковый для человека; фактический `turn_id` виден в технических деталях. Выбор не отправляет новую реплику и не меняет текущую тему.

Блоки расположены в порядке:

1. **Что услышали:** исходный транскрипт, канал, язык, языковые сегменты при наличии.
2. **Выбранный маршрут:** все выбранные сценарии в фактическом порядке, ID, локализованное название, приоритет. У основного — более заметная рамка, а не увеличенный рекламный баннер.
3. **Почему этот маршрут:** короткое переданное `reason`, основанное на признаках запроса. Не раскрывать и не генерировать скрытые рассуждения; не добавлять обоснование от фронтенда при отсутствии значения.
4. **Альтернативы:** ID, название, переданная оценка, возможная граница при наличии в данных. Это просмотр кандидатов, не ручной переключатель маршрута.
5. **Параметры:** ключ, понятная подпись, значение, состояние «Известен»/«Нужно уточнить»/«Исправлен». Происхождение показывать только при наличии события. Значение `null` — «Не указано», а не ноль.
6. **Факты и действия:** ссылки на те же источники, реальные статусы операций и подтверждений; имя операции раскрывается в деталях.
7. **Время:** этапы и фактический итог согласно 11.2.
8. **Доска:** раскрываемый список исходных `BoardEntry` выбранного хода с временем, автором, типом и payload. Понятное представление не изменяет исходную запись; рядом доступен исходный JSON.

Оценку показывать как `0,86 · оценка модели`, пояснение «Значение не является проверенной вероятностью правильного ответа». Не писать «Точность 86%». Если выбранный формат содержит одну оценку всего решения, не копировать её каждому сценарию как индивидуальную. Неизвестный ID показывается буквально с предупреждением; frontend не заменяет его похожим.

Во время обработки доступны завершённые блоки и ожидание недостающих; вся панель не заменяется одним spinner. Ошибка загрузки одной реплики имеет локальный retry. При переключении хода старый `reason` не остаётся под новым заголовком.

### 11.2. Замеры

Отдельные строки: «Распознавание речи», «Выбор сценария», «Чтение данных», «Формирование ответа», «Подготовка первого аудио», «До начала воспроизведения». Единица ms для коротких этапов, секунды с одним/двумя знаками для длинных; ноль только для реального нулевого измерения, отсутствие — «Нет замера».

Итоговая задержка — локально измеренный интервал от окончания записи/речи до фактического старта слышимого содержательного ответа. При отсутствии VAD обозначить точку как «От отправки записи», не утверждать точное время конца естественной речи. В случае блокировки autoplay показать причину и включённое пользовательское ожидание; такой замер нельзя незаметно сравнивать с автоматическим воспроизведением.

Серверные этапы и клиентский интервал нельзя складывать или вычитать по абсолютным часам разных устройств. Параллельные чтения не суммируются в общий путь. У фонового поиска отдельная строка/дорожка с подписью «Вне основного ответа». Если общей временной шкалы нет, использовать список длительностей, а не вымышленный waterfall.

Ориентиры «Роутер ≤500 мс» и «Начало ответа ≤1,5 с» можно показать в tooltip «Ориентир ТЗ». Превышение не делает весь разговор ошибочным и не блокирует продолжение. До накопления реальных данных не рисовать среднюю задержку, accuracy, успешность и зелёные SLA.

### 11.3. «Устройство слоя» — обязательный диагностический просмотр

Открывается из «Разбора» в широком drawer или вложенном экране этого раздела. Внутри три вкладки: «Промпт», «Ответ модели», «Доска». Видна привязка к текущей сессии, выбранному ходу и версии контекста.

- **Промпт:** реально переданный системный текст/карточки и доступная обезличенная переменная часть. Есть поиск по тексту и ID сценария, перенос строк и копирование разрешённого фрагмента. Если диагностический endpoint не отдаёт промпт, показать «Реальный промпт пока не предоставлен». Статический пример можно показывать только с заголовком «Образец из документации».
- **Ответ модели:** фактический сырой JSON с подсветкой; отдельный статус валидации, если он предоставлен. Не скрывать неизвестные поля и не исправлять JSON так, чтобы сырой ответ выглядел валидным.
- **Доска:** фактические типы `utterance`, `routing`, `topic_stack`, `slots`, `facts`, `timing`, `action`, автор, время, версия и источник. Фильтры по типу и ходу, строковый поиск по доступному тексту. Служебные поля — здесь, а не на кнопке «Начать разговор».

Ключи и секреты никогда не попадают в этот просмотр. Маскирование персональных данных обозначается явно; после маскирования это «Представление с маскированием», а не точная байтовая копия запроса. Нет данных — соответствующее пустое состояние; не создавать постановочную цепочку решений.

Для небольшого журнала текущего звонка — обычная прокрутка. При большом уже загруженном журнале — «Показать ещё 50», только если действительно есть записи. Не вводить бесконечный polling или виртуализацию заранее.

## 12. «История»: поиск, фильтры, сортировка и пагинация — P1

### 12.1. Состав страницы

Заголовок «История разговоров», подпись об источнике: «Разговоры этой вкладки» для памяти браузера, «Демонстрационные записи» для fixtures либо описание серверной истории, когда она подключена. Счётчик равен реальному количеству доступных записей. Отдельного backend API истории сейчас нет; интерфейс не обещает хранение после перезагрузки.

Панель: поиск; период; результат; язык; сценарий; «Сбросить». На узких экранах остаются поиск и кнопка «Фильтры · N». Под панелью — активные chips, количество совпадений, затем список и пагинация. Во время активной сессии сохраняется полоса звонка.

Десктопные колонки: начало, клиент/«Не определён», краткая тема, результат разговора, язык, длительность, кнопка открытия. ID сессии — вторичная строка или детали. Не добавлять операторскую продуктивность, сумму выплат и эмоциональный рейтинг.

Кликабельное название/кнопка «Открыть» является основным доступным переходом; строка может реагировать на обычный клик, но вложенная кнопка меню не открывает разговор одновременно. Массовых checkbox нет, поскольку массовые действия не предусмотрены.

### 12.2. Поиск

Placeholder «Клиент, тема или номер обращения». Поиск по имени, маскированной доступной части номера обращения/полиса, ID сессии, названию/ID сценария. Не искать скрытый ИИН так, чтобы результат раскрывал его существование.

Debounce 250 мс; Enter применяет сразу; очистка крестиком возвращает полный список с оставшимися фильтрами. Нормализовать регистр и пробелы, сохранять казахские буквы; не смешивать `і` и `и`. Минимальной длины нет для небольшого локального списка. Во время сетевого поиска результат последнего запроса побеждает старые ответы; актуальная строка поиска остаётся видна.

### 12.3. Фильтры

- **Период:** «Все даты», «Сегодня», «Последние 7 дней», «Последние 30 дней», «Выбрать период». По умолчанию «Все даты». Для синтетических историй «Сегодня» = 01.10.2026; это подписано. Для реальной технической истории — текущая календарная дата в часовом поясе интерфейса, отдельно от доменного `DATASET_TODAY`.
- **Результат:** мультивыбор «Завершён», «Передан оператору», «Прерван», «Завершён с ошибкой». Локальное отображение строится из реальных статусов, а недоступные варианты не превращаются в выдуманные записи. «Завершён» означает завершение разговора.
- **Язык:** мультивыбор RU, KK, mixed, «Не определён». Mixed — явный признак хотя бы одной смешанной реплики; сессия с отдельными RU и KK репликами может соответствовать обоим фильтрам без выдуманной сегментной классификации.
- **Сценарий:** поиск по всем доступным 40 сценариям и системным исходам, мультивыбор. Если в разговоре встречается любой выбранный сценарий, он подходит под этот фильтр.

Внутри одного мультифильтра действует OR, между группами AND. Число на кнопке «Фильтры» — количество активных групп без строки поиска. Chips отображают конкретные значения и позволяют удалить одно значение. «Сбросить» очищает поиск и фильтры, возвращает исходную сортировку и первую страницу; выбранный размер страницы сохраняется.

На desktop изменения простых фильтров применяются сразу; в mobile drawer используются черновые значения, кнопка «Показать результаты» применяет их целиком. Закрытие mobile drawer без применения отбрасывает только черновик и сохраняет уже применённые фильтры. «Сбросить» внутри drawer сбрасывает его черновик, результат меняется после применения.

### 12.4. Выбор диапазона дат

Календарный popover: пресеты слева на desktop, один месяц на телефоне, поля «С» и «По» с форматом ДД.ММ.ГГГГ. Можно ввести дату клавиатурой. Начало позже конца — ошибка рядом с полями, применение недоступно. Границы включительны по локальной календарной дате; день не режется сравниванием UTC-полночи. Две одинаковые даты — один день.

Состояние выбора видно и текстом, и заливкой. «Применить» подтверждает диапазон, «Отмена» восстанавливает прежний. В мобильном drawer это подтверждает поле в черновике, а весь набор фильтров применяется общей кнопкой. Не блокировать календарные даты произвольно; неподдерживаемый диапазон должен иметь объяснение.

### 12.5. Сортировка

По умолчанию новые первыми. Доступны сортировка по началу и длительности; по теме и имени — только если полезны в готовой версии. Первое нажатие меняет направление, индикатор и доступная подпись показывают порядок. Одна сортировка за раз, стабильный ID как вторичный ключ. Новая сортировка переводит на страницу 1.

Не маскировать сортировку декоративными стрелками. Если нет серверного контракта сортировки, применять её к полному локальному списку, а не только к текущей странице.

### 12.6. Пагинация

- Размеры: 10, 25, 50; по умолчанию 10.
- Футер: «1–10 из 28», «По 10», кнопки «Назад», номера страниц, «Вперёд». При большом числе страниц — первая, последняя, текущая ±1 и многоточия. Многоточие не кнопка.
- Фильтрация/новый поиск/сортировка/смена размера переводят на страницу 1. При открытии деталей и возврате состояние восстанавливается.
- Если после обновления текущая страница не существует, показать последнюю доступную; при отсутствии результатов — пустой список и без бессмысленного «1 из 0».
- При единственной странице не показывать ряд из disabled-стрелок: оставить количество и размер при необходимости. При нуле записей скрыть весь пагинатор.
- На телефоне — «Назад · 2 из 3 · Вперёд» и компактный выбор размера.
- Во время загрузки следующей страницы controls не допускают параллельных переходов. Ошибка сохраняет последнюю успешно показанную страницу с честной подписью и действием «Повторить».
- Порядок вычисления для локальных данных: поиск → фильтры → сортировка → пагинация. Счётчики и номера берутся из того же набора.
- Если сервер позже отдаёт только курсор и не сообщает total, использовать «Загрузить ещё» по реальному cursor-контракту, без придуманных номеров страниц и итогового количества.

### 12.7. Пустые состояния и просмотр записи

Первое использование: «Здесь появятся завершённые разговоры» и «Перейти к звонку». Фильтр без совпадений: «Ничего не найдено» и «Сбросить фильтры». Ошибка загрузки: пояснение и повтор. Нельзя заменять сетевую ошибку сообщением «Разговоров нет».

Просмотр завершённого разговора: breadcrumb «История / Разговор …», дата, итог, длительность, доступные транскрипт/контекст/разбор. Все бизнес-действия read-only; прослушивание доступно только при наличии реального файла, иначе «Аудио не сохранено». «Новый звонок» начинает чистую сессию, не продолжает прошлое подтверждение.

Экспорт — только выбранной доступной записи согласно разделу 15. Прямой адрес неизвестного ID показывает «Разговор не найден». В памяти вкладки после reload допустимо «Эта локальная запись больше недоступна»; нельзя симулировать серверное восстановление.

## 13. «Сценарии»: полный каталог — P1

### 13.1. Назначение и состав

Каталог объясняет, какие вопросы понимает Voice Router и где проходят границы похожих сценариев. Это справочник на основе `scenarios.json`, не UI редактирования роутера. Полнота маршрутизации 40+3 обязательна независимо от готовности красивого каталога.

В заголовке раздельно: «40 сценариев» и «3 системных исхода», значения вычисляются из данных. Два сегмента «Сценарии» и «Системные исходы». На карточке/в строке: ID, название, короткое назначение, область страхования, приоритет, требование идентификации/подтверждения и действие «Подробнее».

Состояние доступности действий — отдельный признак: «Действия поддерживаются»/«Часть действий через оператора»/«Передача оператору»/«Поддержка не подтверждена». Вызов всех сценариев и выполнение всех действий — разные вещи. Не ставить зелёный «Работает» только по наличию сценария в JSON или плану ADR 0005.

### 13.2. Поиск и фильтры

Поиск по ID, локализованному и исходному названию, описанию и примерам из `scenarios.json`; debounce 250 мс. Ожидаемые ответы `dev_utterances.json` не используются ни как справочник, ни для поиска.

Группы фильтров формируются из реальных полей каталога:

- Область: `auto` — автострахование; `travel` — поездки; `property` — имущество; `accident` — несчастные случаи; `health` — здоровье; `corporate` — корпоративное; `general` — общие вопросы.
- Категория: `sales` — покупка и консультация; `claims` — страховые случаи; `servicing` — обслуживание; `contact` — связь; `feedback` — обратная связь; `info` — информация; `security` — безопасность.
- Приоритет: `normal` — обычный, `high` — повышенный, `urgent` — срочный. Не смешивать high и urgent.
- «Нужна идентификация» и «Нужно подтверждение» — трёхпозиционные значения «Все / Да / Нет», не checkbox, где снятие означает одновременно «нет» и «все».
- Возможности исполнения — только при наличии подтверждённых capability-данных либо с меткой «По плану реализации».

Поиск, OR внутри групп и AND между группами, chips и mobile drawer работают так же, как в истории. Фильтры каталога независимы от фильтров истории. Переход между двумя сегментами сохраняет их собственный поиск, но не применяет бизнес-поля вроде `requires_identification` к системным исходам, где такого поля нет.

### 13.3. Сортировка и пагинация

По умолчанию ID по числовой части: SC01…SC40. Дополнительно «По названию» и «Сначала срочные»; во втором случае urgent → high → normal, затем ID. Смена локали перестраивает алфавитную сортировку, если именно она выбрана.

Размер страницы: 10, 20, 40; по умолчанию 20. Пагинатор повторно использует поведение истории. Для трёх системных исходов пагинация не нужна. При выборе «40» показывается весь реальный набор, а не фиксированные карточки-заглушки. Если когда-нибудь добавится 41-й сценарий, компонент не должен его отрезать из-за жёстко заданной длины массива.

### 13.4. Детальная карточка сценария

Drawer шириной до 720 px на desktop, полноэкранный на телефоне. Заголовок ID + локализованное название; далее:

1. Назначение и условия выбора.
2. «Когда нужен другой сценарий»: все элементы `not_this_if`, ссылки `use_instead` на соседние карточки. **Исходный текст `condition` сохранять дословно**, как требует AGENTS; понятный перевод можно показать отдельно с меткой «Перевод», не заменяя оригинал.
3. Приоритет, `requires_identification`, `requires_confirmation`, при необходимости `fast_path_eligible` в технической секции. Последний флаг не означает, что быстрый путь реализован.
4. Обязательные и необязательные параметры из `slots`, названия через словарь; список — для просмотра, не форма выполнения сценария.
5. Действия из `actions`, фактическая поддержка каждого, очередь handoff если указана. Признак `irreversible: false` не трактуется как отсутствие побочных эффектов.
6. Примеры фраз RU/KK из `examples`, сгруппированные по языку. Кнопка «Скопировать пример» копирует текст; «Подставить в разговор» допустима только как заполнение черновика с явным переходом, без отправки и ручного выбора сценария.
7. Ссылка «Посмотреть исходные данные» раскрывает соответствующий объект JSON. Системный исход отображает свои description/behavior/response, не получает выдуманные бизнес-слоты.

Переход по соседнему сценарию заменяет содержимое того же drawer с возможностью «Назад к SC17»; стек модальных окон не растёт. На ошибке загрузки исходного объекта сохраняется заголовок и кнопка возврата. Отсутствие перевода — исходное название с понятным fallback, а не пустота.

## 14. Выпадающие списки, меню, popover и tooltip

### 14.1. Общая геометрия

Один набор правил для всего приложения. Триггер высотой 40 px, минимум 160 px по ширине для фильтра, для компактных полей размер под содержимое. Popup отстоит на 6 px, радиус 8 px, тонкая граница, одна мягкая тень. Типовой padding 4–8 px, строка 36–40 px. Высота списка максимум 320 px либо доступная высота окна с отступом 12 px; прокручивается список, а не скрытая за ним страница.

Popup по умолчанию открывается вниз к началу триггера, при нехватке места — вверх/в другую сторону. Отступ до края viewport минимум 8–12 px. У длинного текста перенос или двухстрочное описание; не обрезать единственный смысловой вариант до трёх букв. Popup не обрезается `overflow` родительской карточки.

Слои: контент 0, sticky 10, меню/popover 30, backdrop drawer 40, drawer 50, dialog 70, toast 90. Меню внутри модального слоя рендерится над своим контейнером, не за overlay и не делает фон доступным. Это проектные токены, а не набор случайных z-index в компонентах.

Одновременно открыто одно меню данного уровня. Клик снаружи закрывает его, Escape закрывает только верхний popup, затем повторный Escape — drawer/dialog. Закрытие не отправляет форму. После выбора одиночного значения popup закрывается и фокус возвращается на триггер.

### 14.2. Одиночный Select

Для языка UI, размера страницы, сортировки и коротких списков. Подпись поля сохраняется рядом с текущим значением. Выбранная строка имеет галочку и доступное состояние, фокус клавиатуры — отдельную рамку. Не смешивать выбранное значение и hover.

При открытии активен выбранный пункт; стрелки перемещают активный вариант, Enter подтверждает, Escape отменяет незавершённый выбор. Для небольшого списка предпочтителен нативный select, если он подходит дизайну. Custom-компонент реализует полную доступную семантику. Конкретный набор клавиш следует выбранному паттерну и проверяется вручную.

### 14.3. SearchableSelect / Combobox

Для выбора сценария и реплики в длинном списке. Поиск в popup не изменяет значение до явного выбора; очищение поисковой строки не снимает выбранный фильтр. Подпись «Не найдено» отличается от «Загружаем варианты» и «Не удалось загрузить». При наличии ошибочного запроса — локальный «Повторить».

В editable combobox фокус остаётся в поле, активный option управляется корректной ARIA-связью; стрелки и Enter работают по списку, обычное редактирование текста не перехватывается. Escape закрывает список без потери ранее принятого значения. Использовать проверенный паттерн [WAI-ARIA Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/).

### 14.4. Мультивыбор

Для нескольких сценариев/результатов/языков использовать popover с поиском и обычными checkbox, а не притворяться одиночным combobox. Внутри popup Tab последовательно проходит элементы, Space меняет checkbox, Escape закрывает. Выбор не закрывает popup. Триггер: одно значение либо «Выбрано: 3». Выбранные значения видны также в chips ниже фильтров.

Если есть «Выбрать все», подпись уточняет «Все найденные» и действие применяется только к текущим доступным результатам поиска. Частичный выбор имеет indeterminate-состояние. «Очистить» снимает значения данного поля, не соседних фильтров. Не делать скрытых лимитов выбора.

### 14.5. DropdownMenu действий

Используется для «Ещё», действий транскрипта и экспорта. Menu содержит глаголы: «Скопировать текст», «Экспортировать», «Открыть разбор». Основные действия не прячутся только в меню. Опасное действие отделено divider и имеет конкретное название; в первой версии удаления истории нет.

Пустое меню не отображается. Недоступная команда объясняется короткой соседней подписью или tooltip, доступным с клавиатуры. Выбор закрывает меню; последующая загрузка относится к вызванному действию и не держит пустой popup открытым. Сортировка/язык — Select, а не меню действий без selected-семантики.

### 14.6. Tooltip и Popover

Tooltip — только краткое пояснение: задержка появления 400 мс, скрытие без заметной задержки. Он открывается также при фокусе, закрывается Escape, не содержит единственный доступ к важному тексту. Если нужно нажать ссылку, скопировать ID или прочитать длинное объяснение, использовать popover с явным триггером.

Клик по tooltip не должен быть обязательным для понимания кнопки. Иконки «микрофон», «стоп», «закрыть», «копировать» всегда имеют доступное имя. Длинное объяснение `confidence` живёт в popover с заголовком и кнопкой закрытия.

## 15. Диалоги, настройки, сообщения и экспорт

### 15.1. Dialog / Drawer

Modal — для решения, которое требуется до продолжения конкретного действия; drawer — для источника, подробностей, фильтров и настроек. Не блокировать весь звонок modal ради сообщения «Факт найден».

Типовой dialog 480 px, длинная форма до 640 px, внутренний padding 24 px; на телефоне отступ 16 px от края. Заголовок, понятное описание, содержимое, footer с 1–2 действиями. При длинном содержимом прокручивается body, footer доступен, высота ограничена viewport с учётом клавиатуры.

При открытии modal фокус внутри, фон недоступен для взаимодействия, Tab остаётся внутри. Escape закрывает, если это не приводит к ложному утверждению об отмене уже отправленного действия; закрыть UI и отменить серверную операцию — разное. При закрытии фокус возвращается к триггеру. Для потенциальной потери текущей записи initial focus на безопасном действии. Следовать [WAI-ARIA Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

Для подтверждения нового звонка клик по backdrop равен отмене намерения начать новый звонок. Клиентское согласие на изменение контакта оформляется inline-карточкой из раздела 10, не системным модальным «ОК» без параметров.

### 15.2. Настройки — только пользовательские

Открываются из sidebar в drawer. Раздел «Интерфейс»: язык RU/KK; уменьшение анимаций «Как в системе / Уменьшить»; плотность только если готов P2. Раздел «Звук»: включить озвучивание, громкость 0–100%, доступный микрофон при наличии разрешения.

Озвучивание выключено — на экране звонка постоянная компактная подпись «Ответы без звука». Это настройка, не ошибка TTS. В режиме показа голосовой функциональности звук должен быть включён; текстовый режим не выдаётся за подтверждение голосового тракта.

Список микрофонов заполняется реальными устройствами; до разрешения показать объяснение. Переключение микрофона во время записи недоступно с подписью «Завершите запись». При исчезновении выбранного устройства — явное состояние и возврат к доступному выбору, без подмены успешного захвата.

Изменения языка/громкости применяются сразу; на кнопке закрытия не писать «Сохранить», если сохранение уже произошло. Хранить локально можно только предпочтения интерфейса. Если localStorage недоступен, настройки действуют в текущей вкладке без поломки приложения.

Здесь нет выбора LLM, ключей, температуры модели, URL backend, управления агентами и тёмной темы-заглушки. Это параметры интеграции вне клиентского UX или ещё не реализованные возможности.

### 15.3. Toast и встроенные уведомления

Toast — короткий результат небольшого действия: «Текст скопирован», «Файл подготовлен». На desktop справа снизу с отступом от голосовых controls; на телефоне над ними. Максимум три, одинаковые повторения объединяются. Успех исчезает через 4 с, при hover/focus отсчёт приостанавливается.

Ошибка, влияющая на разговор, показывается внутри соответствующего блока и остаётся до изменения состояния или закрытия. Toast не единственный носитель ошибки микрофона, отправки, подтверждения или handoff. Не закрывать ошибки автоматически через 2 с. Уведомление не получает фокус и не перекрывает кнопку остановки.

### 15.4. Экспорт

P1: «Экспортировать разговор» открывает компактный выбор TXT или JSON. TXT — доступный транскрипт и итог; JSON — разрешённые данные с указанием режима и источника, без секретов. Настройки: «Включить доступную трассировку», «Маскировать контактные данные» включено по умолчанию. Если включение полного значения не разрешено источником, переключателя раскрытия нет.

Содержимое формируется из фактически загруженной записи. Если часть трассировки отсутствует, это указано в файле и preview. Не скачивать «всю историю», если загружена только страница. Имя файла `saqta-voice-<session-id>-<date>.<ext>` с безопасным ID. Успех означает создание файла/передачу браузеру, а не проверенное сохранение на диске.

PDF, CSV и экспорт аудио не добавляются в первую версию. Аудио доступно только при существующем файле и согласованном поведении хранения. Локальные object URL освобождаются после использования, raw audio не сохраняется автоматически в localStorage.

## 16. Анимационная система

### 16.1. Общие параметры

Анимация помогает понять смену состояния и расположение элемента. Она не является способом показать вычисления модели. Использовать токены: `motion.instant=0ms`, `fast=120ms`, `base=180ms`, `panel=240ms`, `emphasis=600ms`. Основная кривая `cubic-bezier(0.2, 0, 0, 1)`, выход `cubic-bezier(0.4, 0, 1, 1)`; для линейного уровня/индикатора — linear. Не использовать пружины с заметным отскоком.

Приоритет свойств — opacity и transform; изменения высоты допускаются для короткого accordion с измеренной конечной высотой. Не писать `transition: all`. Входящее обновление прерывает предыдущую анимацию корректно, не ставится в длинную очередь.

### 16.2. Спецификация переходов по компонентам

- **Button:** hover-фон 120 мс, pressed-фон 80 мс; без увеличения/подпрыгивания. Focus ring появляется сразу. Loading сохраняет ширину кнопки, spinner не вытесняет название и не вызывает скачок layout.
- **Sidebar:** переход 216→72 px за 180 мс, только при явном переключении; подписи исчезают за 80 мс, появляются после раскрытия. На первом рендере не проигрывать самопроизвольное сворачивание. P0 допустим мгновенный переключатель.
- **Dropdown / Select / Popover:** вход opacity 0→1 и translateY 4→0 px за 120 мс; выход 90 мс. При открытии вверх направление смещения зеркальное. Размер и anchor вычисляются до появления, чтобы меню не прыгало из левого верхнего угла.
- **Tooltip:** после задержки 400 мс fade 100 мс; выход до 80 мс. Повторный tooltip при движении между соседними кнопками не требует длинной задержки, но не мерцает.
- **Tabs:** активная линия/фон 120 мс, содержимое fade до 120 мс без перемещения всей страницы. При reduced motion содержимое заменяется сразу. Выбор старой реплики в разборе не запускает анимацию каждого вложенного поля.
- **Drawer:** backdrop fade 160 мс, панель translateX от 24 px к 0 и opacity за 240 мс; закрытие 180 мс. Не летит через весь экран. На телефоне полноэкранный drawer может входить снизу на 16 px за 200 мс.
- **Dialog:** backdrop 160 мс, окно opacity и translateY 8→0 px за 180 мс. Без резкого scale и размытия текста. Focus trap активен с открытия, а не после завершения эффекта.
- **Accordion:** раскрытие 180 мс, закрытие 140 мс, поворот caret 90° за 120 мс. Если высота неизвестна или контент длинный, выбрать мгновенную высоту и fade, а не произвольный `max-height: 9999px`.
- **Новая реплика:** opacity 0→1 и translateY 6→0 px за 160 мс только для действительно добавленного элемента. Исторические реплики при загрузке не анимируются каскадом. Автопрокрутка подчиняется разделу 8.5.
- **Изменение статуса:** текст обновляется сразу, лёгкий fade 120 мс; не показывать одновременно «Готово» и «Ошибка» на пересекающихся слоях.
- **Новый факт:** появление 180 мс и краткое мягкое выделение фона до 600 мс. Повторный рендер того же факта не возобновляет подсветку. Метка источника остаётся доступной сразу.
- **Устаревший результат:** одна смена состояния и подписи; не трясти карточку и не окрашивать весь экран красным.
- **Фильтры:** chips появляются/удаляются за 120 мс; список обновляется без каскадного разлёта строк. Пагинация меняет страницу с коротким fade до 120 мс, без горизонтального slide как в фотогалерее.
- **Toast:** вход opacity + translateY 8→0 px за 180 мс, выход 120 мс; соседние уведомления плавно смещаются, не наезжают на controls.
- **Изменение ширины панели, P2:** во время drag нет transition; ширина следует указателю, ограничена минимумами раздела 5. После отпускания не пружинит. Клавиатурная настройка через separator и шаг 16 px, «Сбросить ширину» возвращает default.

### 16.3. Индикаторы ожидания

Skeleton появляется только при фактической загрузке ещё неизвестного содержимого; для очень коротких операций можно задержать его показ на 150 мс, но готовый результат не задерживать ради минимального времени skeleton. Формы и кнопки показывают своё ожидание сразу. Мерцающий shimmer не обязателен: спокойные статичные блоки достаточны.

Spinner означает неопределённое ожидание, не процент завершения. Локальный таймер ожидания допустим с подписью «Ожидаем 4 с»; по таймеру нельзя переходить «роутер → чтения → ответ», если соответствующих событий нет.

Волна записи привязана к анализатору настоящего аудио. Волна ответа — к фактическому воспроизведению, если есть такой сигнал; иначе обычный значок динамика и подпись. Фоновая активность заканчивается по реальному исходу задачи. Не делать постоянный пульс у всех AI-элементов.

### 16.4. Reduced motion и производительность

Учитывать системный `prefers-reduced-motion`; собственная настройка может дополнительно уменьшить движение, но не должна принудительно включать его поверх системного ограничения. Убрать slide, smooth-scroll, пульсацию и shimmer. Состояния, текст и focus сохраняются; мгновенная смена либо короткий fade до 80 мс допустимы.

Анимации не должны задерживать микрофон, отправку реплики, появление текста или измерение первого звука. Измерения начинаются и заканчиваются на событиях аудиотракта, а не на завершении CSS-анимации. На скрытой вкладке не гонять декоративные циклы; после возвращения отражать текущее состояние, не воспроизводить все пропущенные эффекты.

## 17. Доступность, локализация и адаптивная проверка

### 17.1. Доступность

Цель — применимые требования WCAG 2.2 AA; это критерий реализации, а не заявление о уже полученном соответствии. Проверить контраст обычного текста не ниже 4.5:1, крупного текста 3:1, необходимых визуальных границ контролов 3:1. Проверять фактические пары с opacity и фоном, а не только изолированные hex. Источник критериев — [WCAG Quick Reference](https://www.w3.org/WAI/WCAG22/quickref/).

- Семантические nav/main/header, один h1 на страницу; иерархия заголовков без пропусков ради размера шрифта.
- Все действия доступны клавиатуре, focus виден и не скрыт sticky-панелью; ссылка «Перейти к содержимому».
- IconButton имеет осмысленное accessible name; placeholder не заменяет label, описание ошибки связано с полем.
- Не использовать div с onClick вместо кнопки/ссылки; selected/expanded/busy сообщаются корректно.
- Статусы и ошибки не кодируются только зелёным/красным. Срочное состояние имеет слово «Срочно» и значок.
- Обновления объявляются умеренно: краткие статусы через polite live region, критические ошибки без потери фокуса. Каждую сотую миллисекунду таймера и каждый сегмент волны не озвучивать.
- Текстовый ответ всегда доступен независимо от аудио. Не воспроизводить рекламные/интерфейсные звуки успеха.
- Zoom 200%, клавиатура и узкая ширина не скрывают «Остановить ответ». Для плотных диагностических JSON допустим локальный скролл, для всей страницы — нет.
- В full-screen drawer на touch кнопка закрытия имеет достаточную область нажатия, не зависит только от жеста.

Не включать клавишу Space как глобальный старт записи: она конфликтует с полями и скроллом. На сфокусированной кнопке действует стандартная клавиатурная активация. Дополнительные shortcuts — только если явно подписаны, не срабатывают в editable-полях и реально нужны.

### 17.2. Локализация

Язык интерфейса и язык разговора — независимые состояния. Переключение RU→KK переводит навигацию, controls, сообщения и подписи; не переписывает уже полученный транскрипт и не заставляет backend отвечать по-казахски без клиентского запроса. Язык ответа берётся из результата исполнителя/предпочтения клиента по основной спеке.

Все интерфейсные строки через централизованный словарь, без разбросанных ternary по JSX. Основные подписи RU / KK для предварительного макета: «Звонок / Қоңырау», «История / Тарих», «Сценарии / Сценарийлер», «Поиск / Іздеу», «Настройки / Баптаулар». Окончательные казахские формулировки проверяет казахоязычный участник, особенно согласие, ошибки и страховые термины. Непроверенные переводы не выдаются за лингвистически утверждённые.

Значения сценариев, источников, ID и исходный `not_this_if` сохраняются; локализованные названия — отдельный слой. Статус с неизвестным кодом показывает исходный код в доступном виде вместо пустого бейджа. Даты форматируются локально, валюта из данных отображается как `31 200 ₸`; технические ISO-даты остаются в JSON.

Проверить удлинение текста на 30–40%, казахские символы, перенос длинных названий. Статические ширины не должны превращать «Подтверждение устарело» в нечитаемую строку. Подсказки не единственный способ увидеть обрезанное название.

### 17.3. Размеры для проверки

Обязательные ручные точки: 1440×900, 1280×720, 1024×768, 768×1024 и 390×844; дополнительно ширина 360 px. Проверить открытое меню у нижнего края, drawer с длинным источником, телефон с открытой клавиатурой, историю на последней странице и длинную смешанную реплику.

На малом ноутбуке не помещать одновременно три узкие рабочие колонки. На телефоне разговор — основной вид, разбор доступен отдельной вкладкой. Ни один breakpoint не удаляет функциональность остановки, текстового ввода, ошибок и возврата к разговору.

## 18. Состояние фронтенда и границы интеграции

Этот раздел описывает только клиентское состояние и перевод существующих данных в интерфейс. Он не задаёт архитектуру backend, БД, очередей, провайдеров или формат новых API.

### 18.1. Что хранится в представлении

- **Оболочка:** раздел, локаль UI, ширина/видимость панели, настройки motion и звука.
- **Активная сессия:** подтверждённый session ID, generation, актуальная context version, состояние жизни сессии. Идентификаторы и версии приходят из согласованного контракта; frontend не придумывает серверные значения.
- **Ход:** текущий turn ID, состояние отправки/STT/обработки/ответа, пометка отмены. Локальный request token нужен, чтобы игнорировать поздние результаты отменённого запроса.
- **Аудио:** media permission, выбранное устройство, состояние recorder/player, локальный blob до отправки, фактические browser timestamps.
- **Разговор:** доступные сообщения и исходные события, выбранный для разбора ход, автопрокрутка и непрочитанные сообщения.
- **Контекст:** отображаемая проекция SessionContext и отдельно статус помощника. Текущий контекст и исторический снимок не перезаписывают друг друга.
- **Списки:** поиск, применённые и черновые фильтры, сортировка, размер/номер страницы, загруженные данные, независимая ошибка.
- **Overlays:** один выбранный источник/сценарий/диалог и точка возврата фокуса. Меню не хранится как глобальный бизнес-статус.

Нужна одна владеющая область состояния активного звонка выше переключаемых страниц. Не создавать разные сессии в `CallPage` и мини-полосе. Нельзя запускать два микрофона или повторный fetch с побочным действием из-за повторного mount/эффекта React.

### 18.2. Соответствие описанным данным репозитория

- `BoardEntry.turn_id` связывает событие с разбором; `type` задаёт группу; `author` — источник записи; `payload` сохраняется без изменения; `source/source_id` питают просмотр факта; `ts_start_ms/ts_end_ms` — серверные замеры; `context_version` — диагностическая метка.
- `SessionContext.session_id/generation/context_version` задают принадлежность текущему контексту; `client_id` — карточку идентификации; `active_scenario/pending_topics` — темы; `slots_by_topic` — параметры; `pending_confirmation` — preview; `facts` — сведения.
- Для patch используются `session_id`, `generation`, `based_on_turn_id`, `base_context_version`, `client_id`, `facts`. Итог принятия/отклонения должен быть передан владельцем backend. Сам факт получения patch не равен успешному применению.
- Поле `facts[].source_id` не содержит универсальный URL; действие показа источника использует переданный разрешённый фрагмент или согласованный read-handler.
- Указанные документы не дают стабильного уникального ID каждой записи доски, полного формата payload всех типов, статуса background job, событий использования факта, сырого промпта и аудиотранспорта. Их нельзя считать уже существующими полями API.

Если нужен локальный ключ рендера, допустим порядковый ключ неизменяемого snapshot-массива. Он не используется как сетевой cursor и не считается гарантированной дедупликацией событий. Повторная доставка и порядок решаются только по согласованному идентификатору/sequence контракта.

### 18.3. Точки подключения без выдумывания endpoints

Подготовить обработчики уровня UI: начало/завершение сессии, отправка текста/аудио, отмена хода, чтение текущего snapshot/событий, просмотр источника/диагностики, чтение каталога/истории при их наличии. Их имена внутри компонентов не являются опубликованным API.

Сегодня реальный запрос — только `/api/health`. Готовность DB и backend не означает наличие STT/LLM/TTS. Продуктовый статус «Голос доступен» появляется только при подтверждённой capability либо успешной проверке речевого тракта. До этого статус «Сервисы доступны; голосовой путь ещё не подключён» уместен в диагностике.

При подключении брать Pydantic-модели из `backend/app/schemas/`, когда они появятся, и отражать их TypeScript-типами. Все запросы браузера через `/api/*`; никакого доступа к env-ключам речевых провайдеров. Не вводить самостоятельно SSE, WebSocket, polling, BFF, серверные actions или новые route handlers, чтобы обойти отсутствие согласованного API.

Для компонентов достаточно логической модели вида «объект с ID, отображаемым названием, статусом и исходной записью». Сырое событие хранится рядом, а не заменяется удобной копией. Unknown-поля не ломают весь экран; несовместимая схема показывает локальную диагностическую ошибку вместо убедительного, но неверного результата.

### 18.4. Работа с асинхронностью

Результат применяется к UI только если он относится к ожидаемой сессии, generation и актуальному запросу. Закрытие source drawer отменяет его незавершённую загрузку либо игнорирует результат; оно не отменяет сам звонок. При смене списка новый запрос побеждает старый, состояние pagination согласовано с видимым результатом.

Остановленный ход не продолжает аудио после позднего ответа. При смене клиента не показывать прежние данные даже на один кадр. При смене версии карточка явно отражает текущие сведения, старый snapshot остаётся только в историческом просмотре.

При перезапуске backend, который по ADR завершает сессию, показать «Разговор завершён из-за перезапуска сервиса» и «Новый звонок». Не пытаться незаметно воскресить старую сессию с прежним подтверждением. При неизвестном результате операции не повторять её автоматически.

## 19. Данные для проверки интерфейса

### 19.1. Три разных признака режима

1. **Источник предметных данных:** синтетический набор Saqta. Он остаётся синтетическим даже при настоящем LLM и настоящем микрофоне.
2. **Исполнение интеграций:** реальный STT/LLM/TTS, серверный мок либо «Не подключено» — по реальной конфигурации, не по случайному фронтенд-переключателю.
3. **Демонстрация интерфейса:** локальное воспроизведение заранее подготовленных событий. Постоянная метка «Демонстрация интерфейса». Сценарий выбирается явно как история для просмотра; свободная пользовательская фраза не маршрутизируется совпадением с примером.

Не называть синтетические факты «живыми клиентами», а локальную анимацию — «работающим агентом». UI-прототип может демонстрировать состояния без backend, но не закрывает приёмку живого голосового пути. Кнопки, для которых нет обработчика, либо работают с явно локальным результатом, либо имеют понятное недоступное состояние.

## 20. Первый запуск: жюри понимает продукт без объяснений

Это главный продуктовый критерий нашей клиентской зоны. Команда параллельно делает backend, агентную логику и frontend; задача клиента — сделать работу других двух частей видимой и управляемой.

### 20.1. Первые 30 секунд

- **Первые 5 секунд:** человек видит «Голосовой помощник страховой компании», поддержку русского/казахского и заметную кнопку начала. Он понимает назначение продукта без чтения README.
- **До 15 секунд:** рядом с кнопкой видна короткая инструкция «Нажмите, запишите вопрос, отправьте — ответ прозвучит здесь». Один пример вопроса помогает начать, но произвольный ввод не ограничен примерами.
- **После первой реплики:** появляется её распознанный текст, текущий реальный этап обработки, затем ответ. Рядом краткая метка выбранного сценария и кнопка «Почему этот сценарий?».
- **По раскрытию:** видны основание выбора, альтернативы, источник фактов и задержка. При работе помощника видно, какие дополнительные данные он нашёл и когда они пригодились.

На начальном экране допустима одна короткая строка «Ваш вопрос → сценарий → проверенные данные → голосовой ответ». Это пояснение процесса, не анимированная имитация живого выполнения. В терминологии обычного экрана использовать «Распознаём речь», «Выбираем сценарий», «Проверяем данные», «Отвечаем»; названия LLM/STT/TTS, версии и JSON раскрываются в разборе.

Показать возможности кратко: «40 страховых сценариев · Русский и казахский · Объяснение каждого решения». До подключения реального тракта не писать «Всё работает» или «Готово к звонку» только по healthcheck. При недоступности сервиса человек видит причину и доступный следующий шаг.

### 20.2. Демо без длинного обучения

Не делать многошаговый onboarding, стартовый выбор роли, пустой dashboard и обязательное модальное приветствие. Первое основное действие доступно сразу. Небольшая ссылка «Как это работает» раскрывает те же 3–4 шага с объяснением панели; её не требуется открывать для звонка.

По завершении демо человек должен самостоятельно ответить: что распознано; почему выбран маршрут; откуда взяты факты; где видны уточнение/подтверждение/передача оператору; что добавил фоновый помощник, если он включён. Это сильнее набора декоративных KPI.

## 21. Работа в существующем frontend и параллельная интеграция

### 21.1. Разделение зон

Наша зона: `frontend/`, браузерная запись/воспроизведение, UX состояний, TypeScript-отражение согласованных контрактов, визуальная трассировка, подключение через `/api/*`. Backend и агентная логика принадлежат другим участникам. Изменения общего API, env и Pydantic-моделей согласуются с владельцем зоны A; их отсутствие не компенсируется скрытой бизнес-логикой на клиенте.

Рабочая карта фронтенда, которую можно адаптировать под уже появившийся код:

- `frontend/src/app/layout.tsx` — общий язык, metadata, оболочка, область состояния активного звонка при необходимости.
- `frontend/src/app/page.tsx` — основной экран звонка; без отдельного рекламного landing.
- `frontend/src/app/history/page.tsx`, `history/[sessionId]/page.tsx` — P1, список и просмотр истории.
- `frontend/src/app/scenarios/page.tsx` — P1, справочник; детали можно открыть drawer без отдельной страницы.
- `frontend/src/app/globals.css` — семантические токены и глобальные базовые правила. Локальные стили могут быть CSS Modules; не добавлять новую систему стилей только ради названия.
- Переиспользуемые компоненты UI, предметные блоки звонка/разбора/каталога, hooks аудио, словари локализации и адаптер представления данных — отдельные небольшие модули внутри `frontend/src/` по необходимости. Точное дерево не навязывается.
- Локальные UI fixtures отделены от адаптера настоящих API и не попадают в режим живой интеграции случайно.

Не подключать сразу несколько библиотек для одних и тех же меню и состояний. Сначала использовать возможности текущего React/CSS и доступные компоненты; зависимость добавлять только если она экономит время и обеспечивает нужное поведение. Для custom popup разумен один проверенный доступный primitive-набор, если команда выберет его; это предложение, не уже установленный пакет.

Перед кодом прочитать релевантную документацию текущего Next из `node_modules/next/dist/docs/`, как требует `frontend/AGENTS.md`. В проверенном checkout `node_modules` отсутствует: наличие документации нужно проверять в рабочем окружении после штатной установки/запуска, а не утверждать, что она уже прочитана.

### 21.2. Что уточнить по готовым контрактам при подключении

Это вопросы владельцам интеграции по их реализации, а не новая анкета по визуальным предпочтениям заказчика:

1. Методы создания/завершения сессии, отправки текста/аудио, отмены foreground; схемы ошибок и однозначное поведение retry.
2. Итоговый формат router result с учётом расхождения из 1.5; формат payload каждой записи и уникальный ID/порядок событий.
3. Snapshot/transport обновлений, session/generation/version при reconnect и закрытии; исходы принятия background patch.
4. Реально поддерживаемые MIME, лимиты записи/размера, формат возвращаемого аудио, момент доступности текста, сведения о языковых сегментах.
5. Как клиент получает актуальный preview, инвалидирование и итог подтверждения; как отличает неизвестный исход от гарантированного отказа.
6. Доступность сырых промптов, источников и измерений; наличие события использования факта в конкретном ответе.
7. Capability-признаки реального/мок-режима, помощника и поддержанных действий; доступность history/catalog endpoints, если они будут сделаны.

Пока пункт не согласован, соответствующее UI можно проверить на явно отмеченных fixtures; интеграционную готовность не заявлять. Не ждать всех P1 endpoints для подключения живого P0.

### 21.3. Обновления репозитория

Во время параллельной работы регулярно получать изменения и читать diff, особенно `backend/app/schemas/`, API, speech, ADR, главную спеку, datasets и настройки frontend. Новая модель или endpoint может заменить допущение этого документа. Перед обновлением проверить branch/status; не терять чужую работу и не делать автоматический stash/reset при грязном дереве.

На чистом main допустим `git pull --ff-only`. На своей ветке сначала `git fetch origin`, затем изучение изменений; интеграция main выполняется осознанно по правилам команды. Force-push и конфликт требуют анализа, а не механического перезаписывания файлов. Изменение API фиксировать в клиентском адаптере и примерах, не размазывать сетевые форматы по JSX.

### 21.4. Порядок реализации

1. Прочитать свежие правила/контракты, оформить необходимую frontend-спеку в отдельной ветке и первым коммитом по AGENTS. При реализации соблюдать ветку и PR-процесс; не коммитить в main.
2. Оболочка, токены Halyk-подобного зелёного, стартовый экран, голосовые controls и основной транскрипт.
3. Подключить существующие API и реальную запись/ответ; обработать ошибки, отмену и новую сессию до декоративных расширений.
4. Разбор, устройство слоя, контекст, подтверждение, handoff; затем помощник при прохождении командного гейта.
5. Адаптивность, клавиатура, RU/KK и полировка P0.
6. P1 история и каталог со всеми описанными фильтрами/пагинацией; P2 только при наличии времени.

Перед PR запуск и проверки через существующие рецепты `just`, как требует актуальный AGENTS. Не вызывать destructive `just reset` без проверки, что сбрасывается именно допустимое тестовое окружение; не уничтожать данные параллельной работы команды. Если проверка не выполнена, указать это явно. Не добавлять UI snapshot-тесты и тесты на косметику; проверить наиболее важные свойства демо. В коммитах/PR не добавлять подписи AI-ассистентов согласно актуальному правилу проекта.

1. Рабочий frontend внутри существующего репозитория с описанным P0, затем доступным по времени P1; без вмешательства в чужие серверные зоны.
2. Централизованные токены цвета, типографики, размеров и motion, переиспользуемые интерактивные компоненты.
3. Перечень реально подключённых API/событий, отдельно локальные UI fixtures и недоступные пока интеграции.
4. Короткую инструкцию проверки через текущий `just` и 2–3 фразы для первой реплики; экран при этом сам объясняет основное действие.
5. Проверку основных разрешений/ошибок браузера, адаптивности и ключевых сценариев. Оставшиеся ограничения названы прямо.
6. PR по правилам проекта при реализации; описание ссылается на главную спеку и этот frontend-документ, если он перенесён в `docs/specs/`.

Не сдавай только статичную картинку, пустые кнопки или красиво разыгранную историю вместо настоящей интеграции. При оценке фронтенда главное: человек понимает продукт с первого открытия, может провести разговор и увидеть доказательства того, как система приняла решение.
