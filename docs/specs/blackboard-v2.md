# Blackboard v2: пошаговый план и контракт

- Статус: принят к реализации по поручению владельца, 2026-09-23.
- Ветка: `feat/blackboard-context-v2`, база: `main` / `9fe5f47` (PR #7/#8).
- Этот план публикуется отдельным коммитом до изменений кода.
- Решения: ADR 0014, ADR 0011/0012. Приоритет — рабочий сквозной backend и скорость.

## 1. Результат

Один главный streaming-агент и N фоновых работают через структурированный blackboard.
История, исправления, задачи и результаты принадлежат разговору; каждая генерация
получает актуальное представление. Поведение проверяется на чате и голосовом API.
Страховые сценарии остаются адаптером существующего приложения: их каталог не сужается.

Не добавляем новые сервисы, векторную память клиента, автоматические бизнес-действия,
дополнительный LLM-координатор или новый UI. Не обещаем production auth/multiworker.
Продолжаем использовать FastAPI, asyncio и PostgreSQL, публичные фасады модулей.

## 2. Пользовательские сценарии и критерии

1. **Обычный вопрос.** Главный получает релевантные сведения; фон выполняется ограниченно,
   результаты входят в следующий сегмент того же ответа, внутренний текст наружу не выходит.
2. **Дополнение во время ответа.** Новый ввод с явным `interrupt_previous=true` прерывает
   главный ответ и начинает новый; предыдущая неизвестная доставка остаётся unknown.
   Старый контракт без этого флага сохраняет 409 для активного ответа.
3. **Исправление данных.** Обновление ключа создаёт новую запись с `supersedes`, старый факт
   остаётся в журнале; зависящие от него выводы/запуски становятся неактуальными.
4. **Несколько задач.** В разговоре есть именованные `task_id`; для каждой свои факты,
   состояние и фон. Результат задачи A не подмешивается в ответ по задаче B.
5. **Пауза и возвращение.** Задачи active/paused/completed/cancelled; при возвращении
   сохраняются действующие записи, просроченные и зависимые от заменённых исключаются.
6. **Перебивание.** Отдельны остановка ответа, остановка фоновой работы и отмена задачи.
   Никакая из этих команд сама по себе не выполняет отмену бизнес-операции.
7. **Поздний результат.** Принимается только при действующих зависимостях. По умолчанию
   сохраняется для следующего ответа, не запускает неожиданную речь. В public trace —
   только обезличенные статусы/идентификаторы, не сырой результат.
8. **Reconnect.** Повтор входа с тем же request_id не создаёт второй ход/запуск.
   Чтение сохранённого SSE по cursor не запускает модель заново. Отсутствие ACK = unknown.

## 3. Разделение ответственности

- `context`: единственный писатель sessions/board_entries, типы blackboard, чистые правила
  актуальности, единая проекция истории и представление для router/handoff.
- `kernel`: scheduling, актуальность задач агента, генерация сегментов, tools, API управления.
- `call`: существующий текстовый/голосовой pipeline, стабильный request_id, replay и cancel.
- `knowledge`, `speech`, `executor`: публичные интеграции без прямого доступа к их хранилищу.

Данные blackboard живут внутри существующего JSONB kernel projection; журнал изменений
append-only в board_entries. Миграция таблиц для v2 не требуется, старые записи получают
безопасные значения при чтении. Версии схемы и границы размера валидируются.

## 4. Данные blackboard

### Задача

`task_id`, `title`, `status` (active/paused/completed/cancelled), `version`.
В сессии есть `active_task_id` (фокус ответа), несколько задач могут быть active.
Дефолтная задача `default` сохраняет совместимость существующего API.
Пауза сохраняет знания; cancel прекращает работу задачи; reopen/resume явный.

### Запись

`record_id`, `key`, `task_id` (null для общих сведений), `value`, `source`, `source_id`,
`version`, `status`, `supersedes`, `depends_on`, `expires_at`, `created_at`.

- Источники: user/tool/agent/system; вывод агента не объявляется доказанным фактом.
- Замещение по (scope, key), ссылки на прошлые записи сохраняются.
- Публикация может передать expected_record_id для защиты от конкурентной правки.
- Зависимости — конкретные версии записей; замещение/истечение срока отзывают вывод.
- Факты независимых фоновых задач не конфликтуют из-за одного глобального context_version.
- Пустой результат, ошибка и отсутствие факта различаются.
- Неизвестные зависимости отклоняются, циклы не допускаются.
- В API ограничены размеры записей, число задач и зависимостей.

### Актуальность запуска агента

`generation` сохраняет изоляцию после reset/смены клиента.
AgentSpec получает `reads`: ключи blackboard, от которых зависит запуск.
Дефолт `['$message']` сохраняет прежнее безопасное поведение на новую реплику.
Явные reads позволяют сохранить полезный запуск через новую независимую реплику.
В этом режиме агенту не передаётся скрытая неучтённая история: только выбранные записи,
задание и источники. Fingerprint учитывает и отсутствующие ключи, чтобы появление значения
тоже инвалидировало прежнее чтение. Результат записывается только при совпадении зависимостей.
Запуск связан с task_id; queued/running/completed/failed/stale/cancelled остаются наблюдаемыми.

## 5. Единая история и ContextPackage

Одна функция в context формирует диалог из доменных реплик и kernel-сегментов,
объединяя их по turn_id/role без повторов. Она используется router, handoff и kernel API.
Системные/template ответы также сохраняются, прерванный streaming не исчезает.

- Полный сгенерированный текст остаётся во внутреннем журнале.
- Каждая часть ответа имеет delivery heard/partially_heard/unheard/unknown (старый контракт).
- Для текстового ACK сохраняется mode=text: это доставка отображения, не доказательство чтения.
- Без audio/text alignment частично услышанный сегмент не режется на слова по пропорции.
- Роутер получает delivery, источники фактов и текущую задачу.
- Пакет модели содержит текущий ввод, неизменяемый prefix, выбранную задачу, актуальные
  записи, источники, последние реплики и ограниченную сводку более старых событий.
- Сводка извлекает факты/открытые задачи; не выдумывает выводов, исходные события доступны.
- Тяжёлые tool outputs не копируются каждому агенту; детальные данные доступны через read tool.
- Ограничение размера действует на весь пакет; текущий ввод и обязательные параметры
  сохраняются, обрезка источников/истории обозначается метаданными.

## 6. API и совместимость

### Существующие

`POST /sessions`, `/turns`, `/interrupt`, `/playback`, `/close`,
`GET /sessions/{id}/events|history|trace` и `/calls/*` сохраняются.
Новые поля запросов optional; существующие tests/клиенты продолжают работать.

### Дополнения kernel

- TurnRequest: `task_id='default'`, `interrupt_previous=false`, `updates=[]`.
- AgentSpec: `reads=['$message']`; task scope задаётся запуском.
- `POST /sessions/{id}/tasks`: создать/обновить задачу, status/focus, request_id.
- `GET /sessions/{id}/tasks`: безопасный список задач и активный фокус.
- `POST /sessions/{id}/records`: внести исходное сведение/исправление с request_id.
- `GET /sessions/{id}/records`: метаданные актуальности, без внутренних agent/tool payload.
- `POST /sessions/{id}/background/cancel`: остановить фон выбранной задачи без остановки речи.
- Все мутации идемпотентны; повтор request_id с иным телом даёт 409.
- Новые события задач/записей внутренние; наружу допускается только metadata, без value.

### Call ingress/replay

- TextTurn получает optional request_id, task_id, interrupt_previous, updates.
- AudioTurn получает optional request_id; стабильность повтора проверяется по fingerprint
  аудио/языка. Сырые аудиобайты в журнал не кладутся.
- События /calls получают cursor и сохраняются для replay без повторной генерации/TTS.
- `GET /calls/{id}/events?after=...` читает только public call events; начальный POST сохраняется.
- Disconnect прерывает незавершённый foreground; reconnect воспроизводит сохранённые
  события и их финальный статус. Возобновление LLM с середины потока не имитируется.

### Интерпретация естественного языка

Ядро принимает явные task/update/cancel команды от интегратора. Оно не классифицирует
страховой сценарий по ключевым словам. Существующий call bridge передаёт изменения
слотов/задачи из результатов router/executor. Самодельный NLP-классификатор не добавляется.

## 7. Пошаговая реализация

1. Проверить fresh main, границы модулей, существующие тесты и локальную БД.
2. Создать отдельную ветку, опубликовать эту спеку и ADR отдельным docs-коммитом.
3. Зафиксировать общие Python/HTTP контракты и владение файлами для параллельной работы.
4. Реализовать типы и чистые операции blackboard: tasks, records, replacement, dependencies,
   expiry, чтение актуального состояния, ограничения и обновление старой JSONB projection.
5. Встроить атомарную запись через Contexts; события и snapshot сохранять одной транзакцией.
6. Свести доменную и kernel историю в одну проекцию с delivery; подключить router/handoff.
7. Обновить ContextPackage: task scope, релевантные записи, ограниченная история,
   извлекаемая сводка, provenance и наблюдаемая обрезка.
8. Перевести scheduling на task + fingerprint, сохранив DAG и лимиты параллельности.
9. Инвалидировать только зависимые запуски/результаты; новый независимый ввод не отменяет всё.
10. Реализовать task transitions, stop background и поздние результаты без самовольной речи.
11. Добавить optional interrupt_previous и updates в kernel submit, сохранить immutable prefix.
12. Добавить tools чтения blackboard в интерфейс агента с ограничением доступного scope.
13. Подключить новые HTTP endpoints, validation, idempotency и безопасную metadata projection.
14. Обновить /calls: стабильный request_id, persisted public replay, новый input contract,
    связь executor slots с blackboard; сохранить event names и voice playback.
15. Пройти восемь пользовательских сценариев на управляемом provider и реальном PostgreSQL.
16. Выполнить единое независимое ревью итогового diff: races, stale data, утечки, повторные действия.
17. Исправить обнаруженное, повторить затронутые проверки, обновить README/спеки и статус плана.
18. Commit + push реализации в ту же feature-ветку, проверить remote SHA и сообщить результат.
    Main не менять автоматически. Live API не нужен для проверки новых правил orchestration.

## 8. Проверки готовности

- [ ] Plan-only commit опубликован до кода.
- [ ] Старые контракты и tests остаются рабочими.
- [ ] Два фоновых результата одной версии принимаются; чужая задача исключается.
- [ ] Исправление ключа отзывает зависимые выводы, независимые сохраняются.
- [ ] Pause/resume восстанавливают состояние задачи; cancel не отменяет бизнес-операцию.
- [ ] Новый ввод с interrupt_previous не пропускает поздние дельты старого ответа.
- [ ] Router и main видят одинаковую историю, включая interrupted/unheard/unknown.
- [ ] Поздний фон не инициирует голос сам.
- [ ] Повтор /calls с request_id не повторяет роутер, инструменты, TTS.
- [ ] Replay и приватные записи не смешиваются; cursor валидируется.
- [ ] Реальный Postgres persistence/reload, HTTP smoke, backend lint, module-boundary tests проходят.

## 9. Явные ограничения этой поставки

Один worker; durable restart задач, multi-tenant auth, автоматическая долгосрочная память,
новый voice UI, реальные STT/TTS и отсутствующий боевой router не входят в эту итерацию.
Казахский semantic-search коллеги подключается отдельной работой после публикации его ветки.
Задачи/параметры из свободного текста определяет существующий router/integrator, а не
эвристики blackboard. Термин «готово» относится к описанным контрактам и проверкам ядра.
