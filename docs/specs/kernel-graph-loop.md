# Граф фоновых агентов: непрерывная работа и доводка фона

- Владелец: зона A
- Связанные ADR: 0015, 0014 (blackboard v2), 0011 (ядро)
- Ветка: `feat/kernel-graph-loop`, база — `main`; этапы 2–3 ребейзятся на `feat/blackboard-context-v2` после его мерджа.

## Цель
Фон должен работать между ходами и попадать в ответ, а не гоняться с первым сегментом.
Плюс убрать три дефекта планировщика: нет ретрая, отказ не доходит до зависимых,
кэш инструментов инвалидируется каждым ходом.

## Этап 1. Независим от blackboard v2

| # | Файл | Изменение | Критерий приёмки |
|---|------|-----------|------------------|
| 1.1 | `kernel/runtime.py` | Ключ `tool_tasks` — `(session_id, name, args)` с TTL и вытеснением по размеру, без `input_revision`. | Одинаковый `rag_search` на двух ходах = один вызов инструмента |
| 1.2 | `kernel/runtime.py` | `existing` в `schedule` считает только `queued/running/completed`; `failed` даёт один ретрай. | Упавший агент перезапускается ровно один раз |
| 1.3 | `kernel/runtime.py` | Родитель `failed`/`stale` → зависимые получают статус `blocked` и событие. | Зависимый агент не исчезает молча, статус виден в `/trace` |
| 1.4 | `kernel/types.py` | `next_step`: `depends_on: ["knowledge"]`, `on: ["agent.result"]`, инструкция «дополни найденное, не ищи заново». | На ход уходит один поисковый агент вместо двух |

## Этап 2. Граф живёт между ходами

| # | Файл | Изменение | Критерий приёмки |
|---|------|-----------|------------------|
| 2.1 | `kernel/types.py` | `AgentSpec.on` расширяется: `response.completed`, `record.changed`. Дефолт не меняется. | Старые сессии работают без правок |
| 2.2 | `kernel/runtime.py` | После `response.completed` вызывается `schedule(sid, "response.completed")`. | Фон работает, пока клиент слушает |
| 2.3 | `kernel/runtime.py` | Условие «раз на `input_revision`» → «раз на fingerprint своих `reads`». | Изменение записи перезапускает только зависимых от неё |
| 2.4 | `kernel/runtime.py`, `config.py` | Квиесценция + бюджеты `max_runs_per_turn=8`, `max_runs_per_session=64`. | Граф затухает; лимит виден событием `graph.budget_exhausted` |
| 2.5 | `kernel/runtime.py` | Поздний результат оседает записью и не публикует речь. | После `response.completed` без нового ввода публичных событий нет |

## Этап 3. Первый ход

| # | Файл | Изменение | Критерий приёмки |
|---|------|-----------|------------------|
| 3.1 | `kernel/types.py`, `kernel/runtime.py` | `AgentSpec.mode: llm \| reader`. `reader` не зовёт модель: берёт `search_query` из брифа, выполняет `rag_search`/`rag_read`, возвращает факты с источниками. | Ридер отвечает за ~200 мс и попадает в первый сегмент |
| 3.2 | `kernel/types.py`, `kernel/runtime.py` | `AgentSpec.blocking` + `deadline_ms`: главный ждёт блокирующих агентов до дедлайна, дальше идёт с пометкой в пакете. | Ответ не задерживается дольше `deadline_ms` |

## Вне скоупа
Multiworker, durable restart задач, изменение публичного SSE-контракта, авторизация,
учёт токенов (зона tracer), боевые router/STT/TTS.

## Ключевые тесты (`just test`, без LLM)
- `test_graph_loop.py`: агент с `on: response.completed` отрабатывает после ответа; новых публичных событий нет.
- Изменение записи перезапускает зависимого агента и не трогает независимого.
- Самопитающийся агент останавливается на бюджете.
- `failed` → один ретрай; второй отказ помечает зависимых `blocked`.
- Повтор одинакового `rag_search` через два хода — один вызов инструмента.
- `blocking`-агент с истёкшим дедлайном не задерживает ответ.
