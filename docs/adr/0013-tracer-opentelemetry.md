# 0013. Трассировка хода в формате OpenTelemetry

- Статус: accepted
- Дата: 2026-09-23
- Автор: зона A
- Спека: [tracer-module.md](../specs/tracer-module.md)

## Контекст
Панели трассировки нужен путь реплики от запроса фронта до ответа: этапы, тайминги, решение
роутера, источники. Сейчас это разрозненные `timing` на доске и `latency_ms` в `turn.done`.

## Решение
- Модель трассы — OpenTelemetry API + SDK; модуль `app.tracer` — нижний слой без зависимостей от других модулей.
- Браузер присылает W3C `traceparent` — сервер продолжает его трассу; ответ отдаёт `traceparent`/`x-trace-id`.
- Span'ы хранятся в Postgres (`trace_spans`, миграция `0004_trace_spans`) и привязаны к сессии звонка:
  неблокирующая очередь + asyncio-сбросчик пачками; ограниченный буфер процесса — для ещё не
  сброшенного и для запуска без БД. Tracer не импортирует `app.db`: фабрику сессий передаёт `main`.
- API: сквозная трасса звонка по session UUID и история звонков (токены по моделям, этапы, роутер).
- SQL трассируется событиями SQLAlchemy (`db.query`, только текст запроса без параметров).
- Если задан `OTEL_EXPORTER_OTLP_ENDPOINT`, span'ы дополнительно уходят по OTLP/HTTP (например, в локальный Jaeger).
- LLM-span'ы размечаем GenAI semantic conventions (`gen_ai.*`).
- ПД: сырые телефон, ИИН, email, ФИО в атрибуты не пишем; маскирование по ключам и шаблонам — страховка.
  Промпты и транскрипты — только opt-in атрибуты `local.*`: хранятся локально, в OTLP уходят лишь при `TRACE_EXPORT_CONTENT=true`.

## Альтернативы
- Свои JSON-тайминги (`timing` на доске, `latency_ms`) — нет стандартного инструментария и связи с фронтом.
- Langfuse / Phoenix — лишний сервис в compose и внешняя зависимость на хакатоне.

## Последствия
Любой OTel-бэкенд подключается одной переменной. Трассы переживают рестарт; при перегрузке очередь
выбрасывает span'ы (счётчик `dropped`), а не тормозит звонок. TTL трасс пока нет (`TODO(hack)`).
Фоновые `agent.run` переживают запрос, поэтому связаны с ходом link'ом, а не родителем.
